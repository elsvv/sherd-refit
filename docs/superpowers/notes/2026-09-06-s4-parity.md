## 2. Three things measured, not assumed

### 2.1 `safetensors` 0.8 cannot carry a multi-key metadata map reproducibly

D §4.2 describes the cache metadata as a flat string map (`format`, `cache_version`, `algo_ref`,
…). `safetensors::serialize` takes that map as a `std::collections::HashMap` and serialises it in
iteration order, and `HashMap`'s order is randomised per map instance. Serialising the same
twenty-key metadata map four times **inside one process** produced four different headers:

```
round 0: {"__metadata__":{"algo_ref":…,"thick":…,"thick_mode":…
round 1: {"__metadata__":{"name":…,"core_version":…,"res":…
round 2: {"__metadata__":{"format":…,"core_version":…,"cache_…
round 3: {"__metadata__":{"source_path":…,"algo_ref":…,"area…
all four identical in-process: false
```

and a second process gave four more. Two runs of `segment` would then write caches that differ
byte for byte, which is exactly the determinism the plan asks S4 to establish. So the whole
metadata block travels as **one** JSON object under the single key `sherd`; `serde_json` writes a
struct's fields in declaration order, so the bytes are fixed. D §4.2's field names are unchanged
inside it. The tensor half was never at risk: `prepare()` sorts tensors by `(dtype, name)` and
serialises the header from a vector.

`created` from D §4.2's field list is deliberately **not** written, for the same reason — a
timestamp makes two runs of the same input produce different files. `core_version`, `algo_ref` and
`backend` carry the provenance a report needs (D §4.3).

### 2.2 Open3D's OBJ reader is one `f32` ULP off a correctly rounded parse

The `load` stage compares the port's cleaned mesh with the reference's `load.V0` / `load.F0`
coordinate by coordinate. Every PLY collection matches **bit for bit**. The five SfS++ sets are
OBJ, and there 1.7–3.1 % of coordinates differ. The cause is not the port:

* the OBJ's decimals parsed with Python's `float()` are found in the reference's `V0` **0 times
  out of 11 263** (Pot_C_Piece_01), so Open3D is not reading OBJ in `f64` either;
* rounded to `f32`, 10 925 of those 11 263 match exactly and the remaining 338 are **one ULP**
  away — e.g. the file's `7.987201` is `7.98720121` correctly rounded and `7.98720074` in the
  fixture;
* over all five sets the worst deviation is exactly **1.000 f32 ULP** (pot_A, pot_B, pot_C, pot_G,
  pot_H — 1.000 on each), never more.

Open3D reads OBJ through Assimp, whose `fast_atof` accumulates the decimal digits itself instead
of calling the platform's correctly rounded `strtod`, and lands one ULP low on some values. Two
consequences: `tobj`'s `use_f64` feature would **not** close this gap (the difference is in the
reference's parser, not in ours — S2's note attributes it to `tobj`'s `f32`, which is only half the
story), and the `load` tolerance has to be a tolerance. It is one f32 ULP, measured at
`max(|a|, |b|, extent)` so that a vertex near the origin cannot dominate. One ULP at these scales
is 2e-8 to 1e-7 of the mesh — five orders of magnitude below D §10.2's tightest downstream
tolerance — while a reader that actually mis-parsed a file would be thousands of ULPs out.

`F0` stays an exact comparison: an index is an integer, and it is identical on all 68 fragments.

### 2.3 A cache hit has to be the same run as a cache miss

The cache stores `V`, `F` and the scalars, not the derived per-face arrays (D §4.2's tensor list,
and doubling the file to carry 7 floats a face is not worth it). That only works if both paths
derive those arrays the same way, and before S4 they did not: `from_mesh_file` computed the face
normals, areas and centroids in `f64` from the pre-narrowing coordinates, so a fragment read back
from a cache — which only has the `f32` vertices — would have differed from the fragment that
wrote it, by a few ULP in every face normal, on every warm run.

`WorkingMesh::from_parts` is now the only way a working mesh is built: it takes the `f32` vertices
and derives the three arrays from *them*. `crates/sherd-core/tests/fragment_cache.rs` asserts
cold-equals-warm field by field, bit for bit. The change costs nothing measurable against the
reference — the native numbers of §4 are S3's numbers to the digit (worst area deviation 0.354 %
against S3's 0.35 %, `res` 9.544 % against 9.54 %, faces 2.216 % against 2.22 %).

## 3. The cache file

`<out>/cache/<name>.sherd`, a `safetensors` file. Tensors: `V f32[n, 3]`, `F u32[m, 3]`.
Metadata (one JSON object under the key `sherd`): `format`, `cache_version`, `algo_ref`,
`core_version`, `name`, `source_path` (absolute), `source_size`, `source_mtime_ns`,
`source_sha256?`, `target_faces`, `face_budget`, `area0`, `thick`, `thick_mode`, `res`,
`watertight`, `n_boundary`, `n_orig_vertices`, `n_orig_faces`, `backend`, `md_params?`,
`features?`.

Validity (R §3.7, with D §4.3's two version fields in place of `CACHE_VERSION`): same absolute
path, the file still exists, `|Δmtime| < 1 s`, same `target_faces`, same name, same
`cache_version`, same `algo_ref`. A cache that fails any of these is not an error — the fragment is
recomputed, and the reason is logged at debug level.

Deviations from D §4.2, all deliberate:

| where | deviation | why |
|---|---|---|
| flat metadata map | one JSON object under one key | §2.1: a multi-key map is not reproducible in `safetensors` 0.8 |
| `created` | not written | §2.1: a timestamp breaks the determinism gate |
| `labels`, `S`, `sp`, `Pf`, `fp`, `brk_*`, `margin_idx`, `features/*` | not written yet | phase 1b computes them; the reader ignores unknown tensors, so the format grows without a version bump |
| "loading is an mmap plus header parse" | the file is read into memory | `safetensors` 0.8's `read_metadata` validates the header against the *whole* buffer, so a header-only view is not available through the crate. A few MB per fragment; the mmap belongs with the memory work of phase 1e, where D §8's 170-scan budget is measured rather than assumed |
| `face_budget`, `area0` | added | the fixture sink dumps `thick.target` as `{target, area0, faces0, target_faces}` and the parity harness compares both (S3's note §8 asked for this) |

The Python side can read the file. With no `safetensors` in the reference's venv, the format was
parsed by hand (8-byte little-endian header length, JSON header, tensor payload) and
`FY234104_reduced.sherd` came back as `V (38602, 3) float32`, `F (77200, 3) uint32`, max index
38601, and a metadata block whose `thick`, `res` and counts equal what the CLI printed — so
`safetensors.numpy.load_file` plus `safe_open(...).metadata()` will read it as D §4.2 promises.

## 5. The thickness gate

D §10.2's native tolerance on `t` and `thick_mode` is ±2 %. S3 measured that no implementation
which does not reproduce numpy's PCG64 stream can hold it — the reference's own estimate moves by
up to 14.5 % when only the seed changes — and recommended `max(2 %, 3 bins of the reference's own
histogram)`. That is what this harness applies, and the note repeats the recommendation to D §10.2
because it is now the gate a passing run depends on.

The bin width is derived from the fixture itself: `percentile(far, 90) / 60` over the distances of
R §3.2's filtered set, recomputed from the dump's own `thick.idx` / `thick.t_hit` / `thick.prim`
(`filtered_distances`), so it is the *reference's* resolution and not the port's. One bin is 1.7 %
to 5.7 % of `t` on this data.

17 of the 136 native thickness checks are outside D §10.2's own ±2 %, and every one of them is
inside three bins:

| set | fragment | quantity | deviation | bins | widened gate |
|---|---|---|---:|---:|---:|
| pot_A | Pot_A_Piece_04_Mesh | `t` | 6.58 % | 2.86 | 6.90 % |
| pot_B | Pot_B_Piece_08_Mesh | `thick_mode` | 5.76 % | 2.72 | 6.35 % |
| synthetic 20 | frag_019 | `t` | 5.27 % | 2.19 | 7.23 % |
| pot_H | Pot_H_Piece_08_Mesh_DS | `thick_mode` | 5.79 % | 2.10 | 8.28 % |
| synthetic 20 | frag_002 | `thick_mode` | 3.37 % | 1.63 | 6.21 % |

Worst over all 136: **2.86 bins** (Pot_A_Piece_04, the plateau histogram S3 dissected), against the
3-bin gate. The injected column needs no widening at all: it is bit-exact on all 68 fragments.

## 6. Determinism

`sherd-refit-rs segment INPUT --out OUT` twice, into two different output directories, on each of
the eight collections: **68 of 68 caches byte-identical**, 108 MB in total. A third run over the
first directory reports `hit` for every fragment and does not rewrite a single file.

The cache carries no timestamp, no hash-map ordering (§2.1) and no path of its own, and
preprocessing itself is bit-reproducible (S3 §4), so the file is a pure function of the input, the
face cap and this build.

`cargo test -p sherd-cli -- --ignored` runs the same check on the terracotta scans, which the plan
names but which are not in git.

## 8. Using it

```
sherd-refit-rs segment input/test_fragments_1/fragments --out out/terracotta
sherd-refit-rs parity --fixtures output/fixtures/terracotta \
                      --input input/test_fragments_1/fragments \
                      --stage working-mesh                       # native
sherd-refit-rs parity --fixtures output/fixtures/terracotta \
                      --input input/test_fragments_1/fragments \
                      --stage all --injected --details
sherd-refit-rs parity --fixtures fixtures/slab/dump --verify-checksums --stage load \
                      --input fixtures/slab/input
```

`--stage` takes `load`, `thickness`, `working-mesh` or `all` and may be repeated; the stages always
run in pipeline order. `--injected` selects D §10.2's injected column, the default is native.
`--input` is the collection the dump was made from: native mode needs it, and so does any stage the
dump does not carry (the manifest's `collection.input_dir` is not usable — the sink records the
basename, `fragments`, not the path the tool was given). The command exits non-zero on any
violation and prints the failing comparisons, e.g.

```
stage          mode       checks  failed worst/tol skipped status
working mesh   native          8       1     1.67       0   FAIL

fragment                     quantity                   rust        reference   deviation      tolerance status
pieceA                       res                 2.124466181      2.549359319    1.667e-1   1.000e-1 rel FAIL
Error: 1 of 8 comparisons outside their tolerance
```

`--verify-checksums` re-hashes the dump against its manifest first (all 444 files of the terracotta
dump match, 2.3 s).

## 9. What phase 1b inherits

* **The cache grows by adding tensors.** `labels u8[m]` and the ten match arrays slot in beside
  `V`/`F` without a `cache_version` bump; `md_params` is already a field of `CacheMeta`, so R
  §3.7's "recompute only the match arrays when the `mdp_*` differ" is a comparison of that one
  JSON value.
* **A new stage is a new module under `crates/sherd-parity/src/stages/` plus one line in
  `Stage::ALL`.** The CLI picks it up from there — `--stage segmentation` starts working the day
  the module exists. D §10.2's segmentation row wants an area-weighted label agreement, which needs
  the sampling rule of that row (200 000 area-weighted points when the tessellations differ);
  `report::Check` already carries the units it needs.
* **`Check::exact` is the right default for anything derived from injected arrays.** Nine of the
  eleven injected quantities in this step came out bit-identical; when a new one does not, that is
  a finding, not a tolerance to widen.
* **The `load` tolerance is one f32 ULP and nothing more** (§2.2). If a future stage needs the OBJ
  coordinates to agree exactly, the only way is to reproduce Assimp's `fast_atof`, and it is not
  worth it: the difference is 1e-7 of the mesh.
* **D §10.2's native thickness row should read `max(2 %, 3 bins)`** (§5), which is S3's
  recommendation, now load-bearing for a passing gate.
