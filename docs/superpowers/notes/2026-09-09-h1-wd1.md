# H1 — W-D1: what it is, and what the port now does about it

**Date:** 2026-09-09. **Tree:** branch `rust-core`, `cdec069` (the audit) → this note. **Machine:**
Apple M2 Pro, 10 cores (6P + 4E), 16-core GPU, 16 GB, macOS 24.6.0, rustc 1.97.0, `--release`; one
Metal adapter, no software fallback. Nothing above 20 fragments was matched. Task H1 executes
steps 1 and 2 of the audit's plan §E (`notes/2026-09-09-fable-audit.md`).

**The answer in one paragraph.** W-D1 is not in the port, not in the kernels and not in the host
pairing. On this adapter a second process doing compute makes the driver **abort** command
buffers — `MTLCommandBufferStatus::Error`, *"Execution of the command buffer was aborted due to an
error during execution. Internal Error (0000000e:Internal Error)"* — and **wgpu 30.0.1 reports
none of it**: `wgpu-hal`'s Metal `Fence::get_latest` counts `Error` as completion, and its fence
handler sits on the *last* command buffer of a submission while the compute pass that aborts is
number 3 of 5, so `poll(Wait)` and `map_async` both answer `Ok` and the host decodes a buffer the
device never wrote. The audit's §A.1.3 is right in substance and wrong in two details: there is no
"GPU restart" in the console, and the bad readback is not a *recycled* block — it is **the state
block the host itself uploaded**, byte for byte. The port now refuses such a readback (a per-call
nonce, a sentinel fill, six validity checks), answers the whole batch on the CPU and counts it;
under contention `examples/repeat_probe` reports every differing repeat accounted for by a refusal
and none unexplained. The checks also found something nobody was looking for, on their first
production run and on an *idle* adapter: `umeyama_rotation` returns a matrix that is not a rotation
when the covariance comes out rank-1, which is **H1-D1** of §4 and is left open here. *(Closed by task F: `kernels/umeyama.wgsl` completes the basis from the largest singular vector outwards and `synthetic_20` reports 0 corrupt readbacks — `notes/2026-09-09-f-hardening-findings.md` §1.)*

## 1. The reproduction

`examples/repeat_probe`, unchanged from task W, with a loop of
`run --backend gpu input/synthetic_pingsdorf_20/fragments --no-preview --no-meshes --no-refine`
alive in another process (one run of that is 19 s and 289 submissions). Three probe runs:

| condition | PointToPlane | PointToPoint |
|---|---|---|
| idle adapter | 0 of 64 | 0 of 64 |
| a `run --backend gpu` beside it | 0 of 64 | **1, 3 and 4 of 64** |

Which reproduces W §6 exactly, including its two puzzles: `0 device errors`, and a differing
repeat whose candidates report **0 iterations** while the first answer reports 30.

## 2. The six experiments

In the order in which they decide, which is not the order the audit numbers them: E2 sees the
event, E4 proves it reaches the port as success, E1 says what the port then reads, E3 and E5 say
when it happens, E6 closes the one alternative.

### E2 — the console. *Decides "aborted": yes.*

```
/usr/bin/log show --last 20m --predicate 'eventMessage CONTAINS "command buffer was aborted"'
```

During the reproduction window, in **both** processes:

```
02:58:16.331 E  sherd-refit-rs[82677] (Metal) Execution of the command buffer was aborted due to
                an error during execution. Internal Error (0000000e:Internal Error)
02:58:16.331 E  repeat_probe[82652]   (Metal) Execution of the command buffer was aborted …
```

Fifteen such lines in that window, several of them at the *same millisecond in both processes* —
the "innocent victim" shape the audit predicted. What the audit predicted and is **not** there:
no `GPU Restart`, no `IOAF code`, no "innocent victim of GPU restart" string. The console message
is the plain Metal abort, and `Internal Error (0000000e)` is what the driver calls it.

### E4 — read the status. *Decides definitively, and finds a second defect.*

A local `[patch.crates-io]` of `wgpu-hal 30.0.1` under `output/h1/wgpu-hal-30.0.1`
(`output/h1/wgpu-hal-e4.patch`; the `[patch]` stanza was removed before the first commit and
`Cargo.toml` is `cdec069`'s again).

**First form** — log `status` and `error` inside the existing `addCompletedHandler` block
(`metal/mod.rs:756`), which is where the audit points. It fired **zero** times under contention:
all 136 handler invocations of one probe run reported `MTLCommandBufferStatus(4)` = `Completed`
with no `NSError`, in a run where the console recorded an abort **in that very process**.

**Second form** — a handler on *every* command buffer of the submission. The abort appears at
once, and always in the same place:

```
[E4] command buffer 3 of 5 ("icp point", fence value 267) ended with status
     MTLCommandBufferStatus(5): Internal Error (0000000e:Internal Error)
```

So there are **two** upstream defects and the audit had read one of them:

1. `Fence::get_latest` treats `MTLCommandBufferStatus::Error` as `Completed`
   (`wgpu-hal-30.0.1/src/metal/mod.rs:1272-1284`) — the audit's citation, exact;
2. the fence's completion handler is attached to `command_buffers.last()` **only**
   (`metal/mod.rs:737-770`), and a wgpu-core submission built from one of our encoders is *five*
   command buffers — `PendingWrites`, `Transit`, `Pre Pass`, our labelled compute pass, and the
   one wgpu relabels `"(wgpu internal) Signal"`. The compute pass is index 3; the fence watches
   index 4, which completes normally. On this workload defect 2 is the load-bearing one and
   `get_latest`'s `Error` arm never even runs.

The status read is what makes this decisive rather than circumstantial: over the final contended
pair of probe runs the patch logged **29 aborts**, the port refused **29 readbacks**, and **29
repeats differed** — one, one and one.

wgpu-core inspects command-buffer status nowhere, so neither reaches the caller. `poll(Wait)`
returns `Ok`, `map_async` fires `Ok(())`, `Stats::errors` stays 0 — which is why W read
"0 device errors" as evidence and why that counter is now `host_errors` (§3).

The upstream report the audit asks for is written as
`notes/2026-09-09-wgpu-fence-report.md`. **It has been filed nowhere**; the decision is the user's.

### E1 — sentinel fill. *Decides "unwritten" against "computed differently": unwritten — and it is the input.*

Every readback buffer is now created `mapped_at_creation` and filled with
`buffers::SENTINEL = 0xFFFF_FFFF` (a NaN as `f32`, `u32::MAX` as `u32`), and a refused readback
logs its census. Over the **32 refused readbacks** of the E1, E3 and E5 runs:

| census | count |
|---|---|
| words still the sentinel | **0, every time** |
| words exactly zero, of 1088 | **512** (22 of 32), else 256–498 |
| words not finite | 0 |

Two things follow, and the second is the one that decides the mitigation.

* **The copy ran; the dispatch did not.** Not one sentinel word survives, so
  `copy_buffer_to_buffer` executed and overwrote the whole staging buffer. What did not execute is
  the compute pass — which is exactly the command buffer E4 catches aborting.
* **The block is the host's own upload, unchanged.** 512 is not an accident: the uploaded state of
  one candidate carries four zeros inside its near-identity rotation rows and four more in words
  12–15, and 8 × 64 = 512. Word 16 still holds the nonce the host wrote rather than `nonce + 1`.
  The 256–498 cases are mixtures — some candidates finished, the rest untouched (E6).

The audit's reading was "zero pages, or the previous buffer of the same size that Metal's
allocator handed back". Neither. **A recycled or zeroed block would have been caught by a
finiteness or a range check; the uploaded initial state passes every check a decoder can make
about a pose**, because it *is* a pose — the one the rung was asked to start from. That is why the
nonce, and not the range checks, is the load-bearing part of §3.

It also explains W's two puzzles at once: `applied` word 0 → "0 iterations", and the pose is the
initial pose narrowed through `f32` and widened back, which is *near* the initial pose but not bit
for bit — so W's probe, which tested equality with the initial pose, said "no".

### E3 — interleave the estimators. *Kernel-specific, but not exclusively.*

`repeat_probe` gained an `interleaved` mode that alternates the two estimators call by call, which
removes the confound the audit names (W's table is also a record of *when* the other process was
busy). Interleaved, under a `run --backend gpu` contender: 4 aborts, **all four on `"icp point"`**,
none on `"icp plane"` — so the asymmetry is real and not an artefact of the order.

It is not immunity, though. Under E5's heavier contention the plane kernel aborts too: 3 plane / 7
point in one run, 6 plane / 9 point in another. What the two kernels differ in is how long one
command buffer runs — `point_to_point` makes **two** passes over the source per iteration (the
means, then the covariance) where `point_to_plane` makes one — and a longer compute pass is a
bigger target. Stated as a correlation, because a mechanism inside the driver is not something
this machine can measure.

### E5 — the shape of the foreign load. *Not the foreign process's big dispatches.*

The audit's hypothesis was that the aborts come from a watchdog or fault in the *other* process's
12 M-query coarse dispatches. Replacing the contender with a **second `repeat_probe`** — small
dispatches only, no coarse kernel at all — makes it *worse*:

| second process | aborts in the probe |
|---|---|
| `run --backend gpu` on `synthetic_20` | 3–5 per 128 calls |
| another `repeat_probe` | **10 and 13** per 128 calls (both processes) |

Two processes with compute in flight on this adapter is the whole condition. The size and shape of
the foreign work is not it.

### E6 — the per-iteration trace. *A.1.4 has no evidence; run in the form the data allows.*

E6 exists to separate an aborted buffer (A.1.3) from a driver defect corrupting a reduction
mid-kernel (A.1.4): *"garbage from iteration 0 is A.1.3; a one-ULP drift from iteration k is
A.1.4."* The nonce answers that per **candidate** without a debug binding: a candidate whose word
16 holds `nonce + 1` reached `store_state` and finished the whole rung; one that still holds
`nonce` never started; anything else is the third class a drift would live in. `icp::receipts`
reports all three on every refusal. Over the 29 refusals of the final contended pair of runs:

| finished the rung | 0 | 16 | 20 | 32 |
|---|---|---|---|---|
| refusals | 13 | 7 | 1 | 8 |

and **`carry neither receipt` was 0 in all 29**. The finished counts are multiples of 16, which is
the granularity at which this GPU retires workgroups. Every candidate is either the answer or the
input; there is no candidate in an intermediate arithmetic state, so there is no first divergent
iteration to report and nothing for the trace to trace. The debug binding E6 describes was not
written; if a refusal ever reports `neither > 0`, it becomes necessary again and `receipts` is
what will say so.

### The verdict

The cause is named: **a command buffer the driver aborted, resolved as success by wgpu's Metal
fence.** E4 measures it directly and E1 measures its consequence; E2 corroborates from the
system's own log; E5 narrows the trigger; E3 says which kernel meets it most often; E6 rules out
the one secondary hypothesis the audit kept. Every differing repeat of every contended run in this
task is matched one-for-one by an abort, and the audit's §A.1.3 is confirmed with two corrections:
there is no GPU restart in the console, and the bad readback is the host's own upload rather than a
recycled block.

The audit asks for "the cause, or the two experiments that rule the leading hypothesis out". The
cause is E4's; E2 and E1 are the two that would have ruled it out had it been wrong, and both
confirm it instead.

## 3. What was shipped (audit §A.1.6)

| | change | where |
|---|---|---|
| 1 | **A per-call nonce.** The host writes an exact `f32` integer below `2^23` into word 16 of every candidate's state block; the kernel gives back `nonce + 1`. The coarse kernel does the same with a `u32` in the word past the last pose, written by each chunk's first workgroup. `STATE_WORDS` 16 → 17 | `icp.rs`, `coarse.rs`, `kernels/icp.wgsl`, `kernels/coarse.wgsl` |
| 2 | **Validity checks.** `registration`: every word finite, the nonce, the rotation orthonormal to 1e-3 **and** `|det − 1| ≤ 1e-3` (corrected here by V7-D2: what the code has always required is the second, which also refuses a reflection, and not the weaker `det > 0` this row used to say), `0 ≤ count ≤ n_src` and integral, `error² ≥ 0`, `0 ≤ iterations ≤ max_iter` and integral, the convergence flag 0 or 1. `counts_of`: the nonce, and `agree ≤ points` for every pose | `icp::registration`, `coarse::counts_of` |
| 3 | **A refused block delegates the whole batch.** `IcpKernel::run` and `CoarseKernel::run` return `Device` / `Cpu` / `Corrupt(why)`; `Corrupt` sends the batch to `CpuExecutor`, logs `why` at `warn` and increments the new `MethodStats::corrupt`, which the run's device lines print | `icp.rs`, `coarse.rs`, `executor.rs` |
| 4 | **Sentinel-filled staging.** `buffers::staging` and `buffers::output` are `mapped_at_creation` and filled with `SENTINEL`; `buffers::census` is what a refusal reports | `buffers.rs` |
| 5 | **`errors` → `host_errors`**, documented as what it can see and cannot | `executor.rs`, D §7 |
| 6 | **D §7's row and `info`** carry the diagnosis and the operational rule; D §6.8 gains the readback-validation block | the spec, `main.rs::info` |

One refused block condemns the **whole** batch, because a readback is one copy of one buffer: a
block the device did not write says nothing about the blocks beside it, and E6's mixtures are the
proof that "some candidates are fine" is a real state.

**Why the nonce and not only the checks.** E1: the bad readback passes every range and finiteness
check, because it is a pose the host itself uploaded. Without the nonce the mitigation would have
caught nothing at all on this machine.

**The wrap.** The `f32` counter cycles at 8 388 600 calls, so a *stale* block that old would pass;
a run makes a few thousand. The coarse `u32` nonce lives in `0x8000_0000 ..= 0xFFFF_FFFE`, so
neither zero nor the sentinel can be mistaken for one.

## 4. H1-D1: what the check caught on its first production run, and it is not a corrupt readback

`--backend gpu` on `synthetic_20`, **idle adapter**, reports `1 corrupt readbacks` on every run,
deterministically. The refusal says why:

```
candidate 146 of 211: the rotation is 1.000e0 from orthonormal, over 1e-3
  (it reports 566 correspondences of 566 after 2 iterations);
  211 of 211 candidates finished the rung, 0 were never started, 0 carry neither receipt;
  readback 3587 words: 0 still the sentinel, 10 zero, 0 not finite
```

Every receipt is present, every word is finite, nothing is a sentinel: **the device ran the rung
and returned a matrix that is not a rotation.** `kernels/icp.wgsl`'s `umeyama_rotation` completes a
rank-deficient covariance by cross products — its own comment says so, *"an orthonormal
completion, which is what keeps the result a rotation when the covariance is rank-deficient"* — and
the completion is written for **rank 2 only**:

```wgsl
if (s[2] <= 0.0) { u[2] = cross3(u[0], u[1]); v[2] = cross3(v[0], v[1]); }
if (s[1] <= 0.0) { u[1] = cross3(u[2], u[0]); v[1] = cross3(v[2], v[0]); }
```

At **rank 1** — `s[1] = s[2] = 0`, which is what a set of collinear correspondence displacements
gives — the first line computes `u[2]` from a `u[1]` that is still zero, so `u[2] = 0`, and the
second then computes `u[1] = cross(0, u[0]) = 0`. At rank 0 the whole matrix is zero. Either way
`det = 0` and `max |RᵀR − I| = 1.0`, which is the number the refusal prints; the two cannot be told
apart from the state block alone, and telling them apart needs the covariance, which never crosses
the bus.

This is a **pre-existing defect of the kernel**, not of task H1 and not of W-D1; the audit's
orthonormality check simply found it the first time it ran. It is recorded here as **H1-D1** and
was **fixed in task F** (`notes/2026-09-09-f-hardening-findings.md` §1); this task did not fix it: `umeyama_rotation` is R §5.4's estimator, so completing its rank-1 and rank-0 cases is a
change to the algorithm with `gpu-check`'s stage-1 rows to re-argue, which is neither of this
task's two steps.

**What it costs meanwhile.** One 211-candidate stage-1 rung of `synthetic_20` is answered by the
CPU executor — which is R §5.4's own answer to it, in `f64` — instead of by the device. The
consequences, measured:

| | before H1 (`cdec069`) | after |
|---|---|---|
| `icp` calls on the device | 134 of 1116 | 133 of 1116, 1 refused |
| `--backend gpu` candidates | 376 (W §6, W §8) | 376 |
| used joins | 19 (W §8's row) | 19 |
| the poses of the batch's pair | the device's `f32` | the CPU's `f64` |
| two GPU runs of the set | byte-identical | byte-identical |
| GPU against CPU: candidates, used joins, groups | identical | identical |

So a `--backend gpu` run of `synthetic_20` now writes different *numbers* for the pairs that rung
touched — the difference this task's brief asks to be named — and the same *decisions*, which is
what D §10.4's run-level rows are stated over. The other six development collections are
unaffected: `terracotta`, `pot_A`, `pot_B`, `pot_C`, `pot_G` and `pot_H` all report **0 corrupt
readbacks** on an idle adapter (`terracotta`, `pot_G` and `pot_H` send no ICP rung to the device at
all).

## 5. What the mitigation costs

One memset per readback buffer (14 KB for a 211-candidate ICP call, 1.5 KB for a coarse call of
370 poses), one word per candidate on the bus, one branch per candidate on the way out, and a
decode that is 17 comparisons against a rung of 30 iterations × 566 points × 211 candidates.

`bench input/synthetic_pingsdorf_20/fragments --backend gpu`, warm, previews and meshes off,
matching stage:

| | rounds | median |
|---|---|---|
| task W (`215f761`, §7) | 11.14 / 11.34 / 11.70 s | **11.34 s** |
| this tree | 11.61 / 11.04 / 11.10 s | **11.10 s** |

Inside the run-to-run spread, and that comparison already carries H1-D1's delegated rung. The
device counters of a `run --backend gpu --no-preview --no-meshes --no-refine`, warm and idle:
`coarse` 380 calls, 151 on the device, 151 dispatches; `icp` 1116 calls, 133 on the device
(134 before), 0 host errors, 1 refused; device memory 70 MB at the peak, 0 batches refused,
0 waits.

## 7. What this does not fix

* ~~**H1-D1 is open** (§4): the kernel's rank-deficient `umeyama_rotation`. Until it is fixed one
  `synthetic_20` stage-1 rung is the CPU's on every `--backend gpu` run.~~ **Closed by task F**:
  the completion is written from the largest singular vector outwards, rank 0 returns the identity
  as `nalgebra` does, a device test covers ranks 0–3, and `run --backend gpu` on `synthetic_20`
  reports **0 corrupt readbacks** with 134 of 1148 `icp` calls on the device — `cdec069`'s number
  — and the same 376 candidates and 19 used joins.
* **A refused batch is the CPU's answer**, so its last bits are the CPU's and not the device's.
  Two `--backend gpu` runs under contention still differ — they differ *legibly* now, with a count
  beside them, rather than silently and wrongly. D §7's operational rule stands and `info` prints
  it: a run whose output has to be reproducible must have the adapter to itself.
* **The upstream defect is untouched.** Until wgpu surfaces the status, every wgpu application on
  a Metal machine with two GPU users has this, and only an application that put a receipt in its
  own kernels can tell.
* **The plane kernel is exposed too** (E3/E5), so this is not a `point_to_point` bug to be
  engineered around.
* **The abort rate is a property of the machine.** 3–13 aborts per 128 dispatches under
  contention here; nothing in the port influences it.

## 8. Housekeeping

`wgpu-hal-30.0.1` and `wgpu-hal-e4.patch`. The `[patch.crates-io]` stanza was added to the

or deleted, and the comparison trees were deleted once measured. The commits are `H1.1`…`H1.4`.
