# E3/E4 — spatial structures: `parry3d` vs Open3D's `RaycastingScene`, `kiddo` vs a hash grid

**Date:** 2026-09-06. Branch `rust-core`. Plan row E3/E4, design `2026-09-06-rust-core-design.md`
(D) §3 rows "radius-bounded NN", "BVH: rays, closest point, inside" and "alternative considered
`parry3d`", §6.2, §6.5, §6.6; algorithm reference `2026-09-06-algorithm-reference.md` (R) §3.2
(thickness rays), §3.4.3 (7-ray cone), §6.1/§6.4 (fracture distance, penetration).
**Machine:** Apple M2 Pro (10 cores, 16 GB), macOS 15.6.1. Shared with other agents throughout;
load average 7–13, so every timing below is the **minimum of 9–15 repetitions across 5 separate
program runs** and both sides were measured alternately in the same windows. Treat single numbers
as ±10 %; the ratios are stable to a few per cent.
**Reference:** Open3D 0.19.0 `t.geometry.RaycastingScene` (Embree 3, float32), numpy 2.5.2,
scipy 1.18.1, Python 3.12.9.
**Candidates:** `parry3d` 0.30.2 (Apache-2.0; `TriMesh` over parry's own `Bvh`) and `kiddo` 6.2.0
(MIT OR Apache-2.0; `ImmutableKdTree<f32, 3>`), against a uniform hash grid written to D §6.2 in
the scratch crate, and against brute force.

## Recommendation

**E4 — use `parry3d` 0.30.2 for the BVH (closest point, bounded closest point, rays), and do the
inside test by ray parity over `TriMesh::bvh()`, never by parry's pseudo-normals.** With that one
substitution it passes the D §3 E4 gate on all ten meshes with a 100× margin: |Δd| ≤ 3.1e-5 on
every one of 300 000 distance queries against a tolerance of 1e-4·t = 6e-4 … 4e-3, zero sign
flips, zero ray hit/miss mismatches in 7.87 M cone rays, and identical primitive ids on all but
five of them. Closest-point queries are **as fast as or faster than Embree single-threaded**
(0.83–1.07× on the ten meshes), the bounded variant is **2.0–3.3× faster than Embree's unbounded
one**, and only ray casting is slower — 2.6–3.2× at one thread, which is inside the "expect 3–5×
slower single-thread" that D §3 already budgeted for its *own* BVH. **The own flattened BVH is
not needed for CPU phase 1** and D §3's three objections to `parry3d` no longer hold at 0.30
(§6). Estimated saving: the 1.5 weeks D §3 costed for the own BVH.

**E3 — use `kiddo` 6.2 on the CPU for phase 1; keep the hash grid for the GPU kernel only.**
D §3's expectation that a hash grid is "≥ 3× faster than `kiddo` bounded queries" **does not
hold**: in the regime that the ICP ladder actually runs in (a pose already close, ≥ 93 % of
correspondences inside the radius) the grid is **1.7–2.1× slower** than `kiddo`, and it only wins
— by up to 3.3× — in the opposite regime where 95–99 % of queries find nothing. `kiddo`'s
`nearest_n(1).within(r)` is the better of its two query forms and is at worst 0.9× and at best
3.5× the grid across every workload measured, so it never loses badly. Both structures were exact
against brute force, index for index, on ≈ 0.9 M bounded queries each per pass. The grid stays in
the design for phase 2 because a KD-tree traversal is a poor GPU fit — but it is now a
GPU-only structure, and the CPU/GPU cross-check of D §6.2 is cheap because both agree with brute
force exactly.

**Two facts for S1 (workspace and CI).** `kiddo` 6.2 requires rustc ≥ 1.89, so the Homebrew
toolchain on this machine (1.88) cannot build it — `cargo build` refuses with *"rustc 1.88.0 is
not supported by the following packages: kiddo@6.2.0 requires rustc 1.89.0, wide@1.7.0 requires
rustc 1.89"*. The experiment ran on rustup stable 1.97.0. Pin a `rust-toolchain.toml` at ≥ 1.89
(`kiddo` 5.3.3 with MSRV 1.85 is the fallback if 1.88 must be supported). And `parry3d`'s
`enhanced-determinism` feature (`simba/libm_force`, `glamx/scalar-math`) builds, reproduces the
default build's results exactly — every E4 accuracy field on all ten meshes, and every E3
correctness count — and costs nothing measurable; it is the obvious setting for D's
cross-platform determinism requirement.

## 1. What was measured and how

Four terracotta working meshes from a fresh `sherd-refit segment input/test_fragments_1/fragments`
(cache version 7) supply the primary data. Because the inside test is the risky part, six more
meshes were added: three `synthetic_pingsdorf_20` fragments (thin-walled, 9.7–17.6 edges per `t`,
200 k faces) and three `sfspp/pot_C` pieces (the coarsest benchmark meshes, 3.1–5.2 edges per `t`,
one of them **not** watertight). Ten meshes, 22 k–200 k faces.

Python dumps, per mesh, exactly the arrays Open3D's scene sees (`V.astype(float32)`,
`F.astype(uint32)`) plus:

- **30 000 query points**, in three groups so that the whole distance range is exercised: 12 000
  surface samples displaced by `N(0, 0.02 t)` along the face normal (the near-surface regime of
  `tight`/`gap`), 10 000 displaced uniformly in ±0.6 `t` (the penetration regime — 11 000–12 500 of
  the 30 000 end up inside), and 8 000 uniform in the bounding box inflated by 20 %.
- `compute_distance`, `compute_signed_distance`, `compute_occupancy` and `compute_closest_points`
  (point **and** primitive id) on those 30 000.
- `compute_distance` on the **fracture-only** scene for 20 000 of them (`Fragment.fracture_distance`,
  R §6.1).
- The **7-ray cone of `classify_faces`** for every face, origins and directions reproduced
  bit-for-bit from the shipped code (`C − FN·1e-3`, `−NS` plus six directions at 15° computed from
  the same `e1`/`e2` basis, with `NS` recomputed through `coarse_grid` + `ball_matrix` +
  `smoothed_normals`): 7.87 M rays over the ten meshes, 0.16–1.40 M per mesh, with `t_hit` and
  `primitive_ids`.
- `MatchData.pc_reg` and `pc_frac` for E3.

The Rust binary reads the same raw f32/u32 blobs, so no mesh format and no conversion sits in the
comparison. Everything is single-threaded unless a column says otherwise; the 4-thread columns use
rayon on the Rust side and Open3D's own `nthreads=4` argument.

Distances: 300 000 unsigned and 200 000 fracture queries, **not one over tolerance**, worst case
3.1e-5 against a tolerance 20–130× larger. The residual is pure float32 summation order — the mean
absolute difference is 7e-8 to 1.5e-7, i.e. one to two ulps of a coordinate.

Rays: **7.87 M cast, 2 hit/miss disagreements** (both on `frag_001`, both rays that Open3D reports
as hits and parry as misses; grazing hits at a silhouette edge), **no Δt over tolerance**, and five
primitive ids out of 7.87 M differ — every one of them on a ray whose `t_hit` agrees to better
than tolerance, i.e. a hit exactly on a shared edge where either adjacent triangle is a correct
answer. That matters for `classify_faces`, which reads `FN[prim]`: two triangles sharing the edge
the ray grazes have nearly equal normals, so the `al > 0.7` vote is unaffected. `Pot_C_Piece_01`
has 3716 rays that both engines report as misses (it is the mesh with a genuine hole).

**Closest points.** The projected *point* differs by more than tolerance on 7–27 queries per mesh
(0.03–0.09 %), and the reported primitive id differs on 12–19 % of queries. Neither is an error:
on every one of those queries the two distances |q − p| agree to ≤ 1.9e-5, so both engines found a
different but equidistant projection — a point on the medial axis, or a projection onto a shared
edge or vertex claimed by either incident triangle. Nothing in R reads the closest *point* or the
closest primitive id; only the distance is used. Worth stating explicitly for the parity harness:
**do not compare closest-point primitive ids, only distances.**

## 3. The one thing that fails: parry's pseudo-normal inside test

`TriMesh` with `TriMeshFlags::ORIENTED` computes vertex and edge pseudo-normals and uses them to
set `PointProjection::is_inside`. On seven of the ten meshes that agrees with Open3D perfectly. On
`frag_001` it does not:

| mesh | watertight | edges per t | sign flips vs Open3D | of which \|d_ref\| ≥ 1e-4 t | worst \|d_ref\| | ray parity (3 axis rays) disagreements |
|---|:--:|---:|---:|---:|---:|---:|
| four terracotta | yes | 17.2–18.2 | 0 | 0 | — | 0 |
| frag_000 | yes | 9.7 | 0 | 0 | — | 0 |
| **frag_001** | **yes** | **12.6** | **30** | **29** | **51.6 (6.6 t)** | **0** |
| frag_002 | yes | 17.6 | 0 | 0 | — | 0 |
| Pot_C_Piece_02, _03 | yes | 5.2, 5.1 | 0 | 0 | — | 0 |
| Pot_C_Piece_01 | **no** | 3.1 | 202 | 202 | 19.7 | 194 |

`frag_001` is a closed, orientable, manifold mesh — 200 000 faces, 300 000 edges, every edge shared
by exactly two faces, no duplicate vertices, no non-manifold edges — and parry still calls 29 of
30 000 points inside that are demonstrably outside: they sit 6.5 to 51.6 away from a surface whose
wall is 7.85 thick. The diagnostic (`E4_DIAG=1`) shows the mechanism: **26 of the 29 project onto a
vertex** (`TrianglePointLocation::OnVertex`), one onto an edge, one at `d ≈ 0`. For those the test
uses the *vertex* pseudo-normal, and on the spiky fracture surface of a synthetically broken mesh —
several of the triangles involved have areas of 1.1e-3 to 1.6e-3 against a median face area two
orders of magnitude larger — the angle-weighted vertex normal points the wrong way, while the
normal of the projected face still points correctly outward (`dot(face_n, q − p)` is +0.79 to +0.93
on those queries). The Bærentzen–Aanæs guarantee needs a non-self-intersecting mesh; a decimated
fracture surface with slivers is not reliably that.

`Pot_C_Piece_01` is the expected case, not a new one: the mesh is not watertight (`closed_enough`
is false), so the signed distance is undefined and *both* methods disagree with Open3D, which is
itself arbitrary there. The pipeline already skips penetration tests for such fragments
(`Fragment.watertight`), so nothing depends on the answer.

**Ray parity, on the other hand, is exact.** Three axis-aligned rays with a majority vote (D §6.2,
R PMC-7) disagreed with Open3D's `compute_occupancy` on **0 of 270 000 queries** across the nine
watertight meshes, `frag_001` included; the one-ray version (Open3D's own rule) also agreed on 0
of 270 000. Implementing it needs no second data structure — `TriMesh::bvh()` is public and
`Bvh::leaves(|node| node.cast_ray(&ray, f32::MAX) < f32::MAX)` yields exactly the triangles whose
AABB the ray crosses, so a Möller–Trumbore count over those leaves is ~30 lines.

It is also cheap. One ray costs 550–950 ns per point single-threaded, three cost 1.7–2.5 µs, and
Open3D's own `compute_occupancy` costs 260–690 ns per point — the same order. In the pipeline the
inside test only runs on points that survive the AABB reject inside the penetration window
(D §6.5), so this is not on the hot path.

Embree is 2.6–3.0× faster per thread and scales better (3.3–4.0× on 4 threads against parry's
3.6–4.0×… in absolute terms 10–13 Mray/s against 2.5–4.0), because it casts ray packets through
SIMD and parry casts one ray at a time. Use `CompositeShapeRef(&mesh).cast_local_ray(…)` rather

**What that costs in practice.** Rays are used only in preprocessing (R §3.2 thickness, §3.4.3
cone). A 150 k-face fragment casts 1.07 M rays; at 1.1 Mray/s that is 0.97 core-seconds against
Embree's 0.35 — **+0.6 core-seconds per fragment**, or +0.25 s wall on 4 threads. Against D §6.6's
1–2 minute preprocessing budget for a 200-fragment collection (200 × 0.6 = 120 core-s = 12 s on
10 cores) that is inside the noise. Matching casts no rays at all except the penetration parity
test, which is 550–950 ns per point on a few hundred thousand points per pair — and there Embree
has no advantage because Open3D pays the same.

## 5. E3 — bounded nearest neighbour on `pc_reg` / `pc_frac`

Four structures on the same clouds: the hash grid of D §6.2 (cell = query radius, open addressing
on `(ix·73856093) ^ (iy·19349663) ^ (iz·83492791)`, `cap = next_pow2(2n)`, 27 neighbour cells in a
fixed order, ties to the lowest index), the same grid with the points stored cell-contiguously,
`kiddo`'s `nearest_n(1).within(r²)`, and `kiddo`'s `nearest_one()` followed by a threshold (the
semantics Open3D's ICP has: unbounded search, then reject). Reference is brute force with the same
tie rule.

Two query sets per cloud, because the two regimes behave completely differently:
**jittered 0.03 t** — every target point moved by a uniform ±0.03 `t`, which is what the ICP ladder
sees once the pose is in the basin, and **displaced 0.5 t** — the whole cloud rigidly moved by
0.5 `t`, which is what the coarse score sees on the ~97 % of hypotheses that are wrong.

The same table over all ten meshes (including the 9 500–12 000-point synthetic and pot C clouds)
moves nothing: the grid's range widens to 83–332 ns and `kiddo within` to 76–275 ns, with the same
ordering in every row.

**Correctness.** Every structure returned the brute-force answer, index for index, on every query:
zero mismatches over ≈ 0.9 M bounded queries per structure per pass, five passes, ten meshes, both
clouds, both regimes, three radii. Zero exact ties occurred, so the tie rule was never exercised on
real data; a synthetic check (`cargo run --example ties`) shows `kiddo` picking the lowest index
among six equidistant points and among five exact duplicates, and returning the same item across
20 rebuilds of the same slice — matching scipy's rule and the grid's, though `kiddo` does not
document this as a guarantee. **Sort the cloud, or accept that a duplicated point may be resolved
either way**; nothing downstream in R depends on which of two coincident points is returned.

**Why the grid loses in the ICP regime.** Its cost is dominated by the fixed 27-cell scan, not by
the distance tests: at r = 0.04 t almost all 27 cells are empty and it still costs 234 ns, more
than `kiddo`'s 110. Storing the points cell-contiguously (a standard fix for the random
`sorted_idx → pts` indirection) changed nothing measurable — ±3 %, within noise — which confirms
the cost is the 27 hash probes, not the point fetches. The grid only pays off when the answer is
usually "nothing within r", because then the probes terminate on empty slots and no distance is
computed at all.

**Build cost, which the ICP ladder pays repeatedly.** The KD-tree is radius-independent and is
built once per pair (0.18–0.22 ms for 5–6 k points). A grid with `cell = r` must be rebuilt for
each of the four ladder rungs (0.06–0.14 ms each, so 0.24–0.56 ms per pair). Another small point
for `kiddo` on the CPU. Grid memory is 462–477 kB per cloud against `kiddo`'s much smaller
footprint; neither matters at these sizes.

**One number D should absorb.** D §6.6 costs the CPU path at "hash grid ≈ 70 ns/query". The
measured floor on this machine is 76 ns (`kiddo within`, small radius, mostly misses — the coarse
score's regime, so that line of D §6.6 stands), but the ICP rungs run at 110–250 ns/query, not 70.
Taking `kiddo within` throughout, the ≈ 17 M bounded queries D §6.6 attributes to one mid-size pair
cost roughly **1.9 core-seconds instead of the 1.67 estimated**, so the "≈ 1.9 core-s per pair,
3.6× over Python" line is optimistic by perhaps 15–25 % — enough to note before the phase-1
benchmark gate, not enough to change any decision.

## 6. What this changes in D §3

| D §3 statement | measured |
|---|---|
| "radius-bounded NN → own hash grid … expected ≥ 3× faster than `kiddo`" | **wrong for the CPU.** 0.47–0.92× in the ICP regime, 0.83–2.02× in the coarse-score regime, never 3×. Keep the grid for the GPU kernel; use `kiddo` on the CPU. |
| "BVH … own flattened BVH … effort ≈ 1.5 weeks … expect 3–5× slower single-thread than Embree" | `parry3d` 0.30 is 0.94–1.15× on closest point and 2.6–3.0× slower on rays — i.e. it already meets the performance target set for the own BVH, for zero weeks of work. |
| `parry3d` "0.17" | current is **0.30.2**; the QBVH has been replaced by a new `Bvh` and the point/ray query surface changed. Pin 0.30. |
| "no bounded closest-point early exit" | **no longer true**: `project_local_point_with_max_dist` prunes by `max_dist`, is exact inside the window (0/300 000 wrong) and is 2.0–3.3× faster than the unbounded call. |
| "f32/f64 duplication" | a non-issue here: R §1 fixes the ray/distance layer at float32 to match Open3D, and `parry3d` is f32-only (`parry3d-f64` is a separate crate that is simply not used). |
| "second layout to maintain for the GPU" | still true, and still a phase-2 cost. It does not argue against `parry3d` for phase 1 — the GPU BVH has to be written for WGSL anyway, and `parry3d`'s `Bvh` is public (`leaves`, `traverse`, `find_best`, `cast_ray`), so a custom traversal can be layered on it without a second tree. |
| pseudo-normal inside test | **rejected.** Use ray parity. §3. |

Two capabilities `parry3d` does *not* provide, for the record. There is no `r_exact` early-out
(PMC-12: stop as soon as the best is below a caller-supplied threshold) — `Bvh::find_best` prunes
by best-so-far only. And there is no batched or packet ray cast, which is most of the 2.6–3.0× ray
gap. Both are addable on top of the public `Bvh` if a profile ever demands it; neither is needed to
pass the phase-1 gates.

## 7. Reproducing

Scratch crate and harness (outside the repo, nothing committed but this note):
`…/scratchpad/rust/E3/` — `dump.py` (Open3D reference dump), `bench_o3d.py` / `bench_build.py`
(Open3D timings, warmed, explicit `nthreads`), `e3e4/` (the Rust harness: `src/main.rs` for E3+E4,
`src/grid.rs` for the hash grid and the brute-force references, `examples/ties.rs`),
`aggregate.py` / `aggregate_e3.py` (element-wise minima over the runs). Run as
`cargo run --release -- <data dir> <threads>` over `data/` (terracotta), `thin/data_synth/` and
`thin/data_potc/`, with `E4_DIAG=1` for the sign-flip diagnostics of §3.

`e3e4_slim/` and `e3e4_det/` are the same harness with `parry3d`'s default features off and,
for `_det`, `enhanced-determinism` added. Both were re-run over all three data directories and
**every E4 accuracy field and every E3 correctness count is identical to the default build's**
on all ten meshes (0 of 480 `bad`, 0 ties, each). Two caveats for anyone re-checking:
their `src/main.rs` is an earlier snapshot that predates the one-ray parity variant and the
`CompositeShapeRef::cast_local_ray` timing, so those two rows exist only in the default build;
and the crate-count figures are `cargo tree --edges normal` unique packages, **63 for the
default build, 58 with default features off** (`spade` is what goes) and 61 for
`enhanced-determinism` — not the 45/40 an earlier draft of this note claimed.
