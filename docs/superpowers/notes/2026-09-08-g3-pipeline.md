# G3 — phase 2c/2d: the software pipeline, and what is really in front of the device

**Date:** 2026-09-08. Branch `rust-core`, from `03027dd` (the head of task G2).
Design references: D §1 (the memory ceiling), §5 (threading, cancellation, progress), §6.3
(buffers), §6.4 (batch formation and the software pipeline), §6.6 (expected speedups), §6.8
(operational concerns), §9 (the CLI), §10.2 (tolerances), §10.4 (test layers), §12 (phasing).
Experiments E1/E2 (where the CPU time goes), E7 (wgpu on Metal), tasks G1 (the device) and G2 (the
two kernels). Machine: Apple M2 Pro, 10 cores (6P+4E), 16-core GPU, 16 GB, one Metal adapter, no
software fallback.

**Verdict: D §6.4's software pipeline is built, it moves the matching stage from 1.0× to
1.04–1.40×, and the thing that now limits it is not a scheduler. The device and the ten cores share
one power and bandwidth envelope: the same 330 submissions of the same work take 5.66 s of device
time with one worker thread and 9.06 s with nine.**

Nothing moved. Every used join, every group and every pose on all seven development collections is
**bit-identical to G2's**, on both backends; parity is 23 804 / 0; the CPU path's outputs are still
`9bf35d6`'s.

---

## 1. What G2 left, and what it turned out to be

G2's open issue 1 read: *"the device is idle 60 % of the matching stage because the pipeline gives
one pair to each rayon thread and they then block on one queue."* The first half was right and the
second half named the wrong queue.

D §6.4's remedy is one sentence — *"CPU threads prepare block k+1 while the GPU runs block k;
double-buffered batches; one submitting thread"* — and the surprise of this task is which clause of
it did the work. It was **"one submitting thread"**, and for a reason the design does not state:
`wgpu::Device::poll` is not a per-thread wait. Every worker that hands a batch to the device calls
`poll(Wait { submission_index })`, all of them take the device's own locks, and the device then
idles while nine threads take turns inside them.

## 2. Step 1: measure first

`samply record` on a warm `synthetic_20`, previews and meshes off, the profile split by
`tools/profile_split.py` (`threadCPUDelta`, so the totals are **core**-seconds over a wall of
16.9 s on a ten-core machine). The stages file is `output/bench_g3/stages_gpu.json`; it adds a
`gpu host prep` row in front of the standard list so that the buffer building, the grid build and
the uploads are separated from the work they carry.

| stage | CPU backend, core-s | GPU backend, core-s |
|---|---:|---:|
| R §5.4/5.6 ICP rungs on the CPU | 41.72 | 34.75 |
| R §5.2 coarse score on the CPU (inside `match_pair`) | 22.90 | 0.07 |
| rayon idle / work stealing | 22.29 | 3.86 |
| pair setup: R §4.2 clouds + KD-trees | 15.18 | 14.47 |
| **R §6 verify** | **12.75** | **12.45** |
| stage 1: breakline ICP | 10.12 | 4.91 |
| refine | 3.62 | 3.32 |
| **gpu host prep (grids, uploads, bind groups)** | — | **1.31** |
| hypotheses, NMS, the rest | 3.72 | 2.94 |
| **total** | **132.3** | **78.2** |

The three questions the task asks, answered:

* **R §6's `bounded_distance` and `inside` are 12.45 core-s, 15.9 % of the GPU backend's core
  time** — about 1.2 s of a 15.5 s stage if it were spread over ten cores. §6 takes this up.
* **CPU preparation between dispatches is 1.31 core-s, 1.7 %.** Building the hash grid,
  interleaving the clouds, creating the buffers and the bind groups is not where the time goes, and
  a device-resident cache for them would buy nothing. That is worth knowing: it is the optimisation
  the design's slot table was for.
* **Idle is the other half of the machine.** The GPU backend already does 54 core-seconds *less*
  work than the CPU backend — the coarse score's 22.9 s went to the device, and with it 18 s of
  rayon's own spinning — and finishes in the same wall time. 78.2 core-s over 15.5 s of wall on ten
  cores is **50 % of the machine**, and the missing half is threads asleep in `poll`.

Three more measurements say the same thing from other sides, and together they identify the lock
rather than the device:

| what | measurement |
|---|---|
| the stage against the worker count (before this task) | 16.08 s at **four** threads, 15.97 s at nine — the CPU work alone would have gone on falling |
| the profile at eighteen threads | **4.9 of ten cores** doing anything; thirteen threads asleep |
| the same 330 submissions | **6.4 s** end to end on one thread, 14 s of wall to drain through nine |

Wall-clock medians before the change (warm, three runs each, `--no-preview --no-meshes`), matching
stage only: `synthetic_20` CPU 15.08 s / GPU 15.52 s (**0.97×**); `pot_H` CPU 7.19 s / GPU 6.84 s
(**1.05×**).

## 3. Step 3: what was built

`sherd_gpu::pipeline::Submitter` — one thread, started with the device and stopped with it, owning
every `submit`, every `poll` and every `map_async` for its life. A worker builds its buffers and
records its command buffer on its own thread (that part is preparation and it parallelises), hands
the finished command buffer and the `MAP_READ` buffer it wants back, and waits on a channel. The
submitter keeps `DEPTH` command buffers in flight.

Three sizing decisions, all measured:

**`DEPTH` = 4, not D §6.4's two.** `synthetic_20`'s matching stage, three runs at each depth:

| depth | matching stage |
|---|---|
| 2 | 12.75, 13.41, 14.62 s |
| **4** | **12.05, 12.13, 12.79 s** |
| 8 | 12.79, 13.61, 14.05 s |

Two is not enough because the submitter has host work of its own between two retires — the map, the
copy out, the reply — and the device drains a queue of one while it does that. Eight is worse than
four: the jobs are queued long before they run and the worker waiting for the oldest waits behind
seven others.

**`Executor::device_slack` = half the pool again.** A worker waiting on the submitter's channel is
a block that is not being prepared, which is D §6.4's own sentence; the pool has to be deep enough
that some other worker is. Two runs each, with the submitting thread already in place:

| `--threads` | pool without slack | with it | matching, no slack | with slack |
|---|---|---|---|---|
| 1 | 1 | 2 | 71.5 s | **37.1 s (1.93×)** |
| 4 | 4 | 6 | 18.7 s | **13.7 s (1.36×)** |
| 9 (this machine's default) | 9 | 14 | 13.0 s | 13.1 s (1.00×) |

It pays exactly where the pool is smaller than the machine and is free where the pool already fills
it — which is what a knob for *covering a wait* should do. This machine's default gains nothing
from it; a four-core laptop gains a third.

**One submission per `Executor` call.** `Kernel::record` records into a caller-owned encoder, so a
call that chunks into three dispatches and then copies its results out is one command buffer rather
than four. `synthetic_20` went from 658 submissions to 330.

`Occupancy` is the fourth piece and it is a measurement rather than a mechanism. The counter that
used to answer "how busy was the device" was the per-thread sum of `submit` + `poll`, which counts
one submission once per waiter: it reported **85.6 s** for a 13.4 s stage. `Occupancy` is the union
of the intervals in which at least one submission was outstanding — the clock starts at 0 → 1 and
stops at 1 → 0 — so nine threads waiting on one submission are counted once. It is an upper bound
on device execution (a submission can sit behind another) and an honest lower bound on idleness,
which is the question.

## 4. What it is worth

Three interleaved runs per backend per collection — `cpu, gpu, cpu, gpu, …` so that thermal drift
hits both alike — warm caches, previews and meshes off. Matching stage, seconds:

| set | CPU | GPU | median ratio |
|---|---|---|---|
| terracotta | 0.74 0.80 0.78 | 0.74 0.69 0.70 | **1.11×** |
| pot_A | 3.75 3.83 4.08 | 3.06 3.05 3.44 | **1.25×** |
| pot_B | 5.10 5.25 4.65 | 3.56 4.32 3.64 | **1.40×** |
| pot_C | 4.57 4.00 4.05 | 3.57 3.57 3.38 | **1.13×** |
| pot_G | 4.03 4.01 3.93 | 4.09 3.83 3.85 | **1.04×** |
| pot_H | 6.95 6.85 7.42 | 6.35 7.36 6.54 | **1.06×** |
| synthetic_20 | 14.58 14.54 14.53 | 13.40 13.03 13.51 | **1.08×** |

Against G2's 1.0× on `synthetic_20` this is the GPU path improving from 15.52 s to 13.40 s while
the CPU control moved 15.08 → 14.54 s, so about 3.6 % of the difference is the machine and the rest
is the pipeline. The device's occupancy went from *at best* 41 % (6.4 s of execution in a 15.5 s
stage) to 68 % (9.06 s outstanding of 13.38 s), and the CPU from 50 % of the machine to 58 %.

## 5. Why it is 1.1× and not 2×, and why no scheduler fixes it

The brief's arithmetic was: 78 core-seconds of CPU work is 7.8 s on ten cores, the device's work is
6.4 s, overlap them and the stage is ≈ 8 s. It is 13.4 s. The reason is in one table — the same
collection, the same 330 submissions, the same work, run with different numbers of worker threads:

| `--threads` | 1 | 2 | 4 | 6 | 9 |
|---|---|---|---|---|---|
| pool (with slack) | 2 | 3 | 6 | 9 | 14 |
| **device with work outstanding** | **5.66 s** | 5.67 s | 6.08 s | 7.62 s | **9.06 s** |
| matching stage | 36.41 s | 23.69 s | 13.84 s | **11.86 s** | 13.38 s |

**The device loses 1.60× of its own throughput as the CPU fills up.** Nothing about the work
changes — the same submissions, the same kernels, the same buffers — only how busy the ten cores
are beside it. On an integrated part that is what sharing a power budget and one LPDDR5 bus looks
like; the two are not independent resources, and a scheduler that overlaps them perfectly is
overlapping them into each other.

The visible consequence is that **the matching stage has a minimum at six workers, not at nine**:
11.86 s against 13.38 s, and 11.86 s against the CPU backend's ~14.5 s is 1.23×. This is not made a
default — `--threads` is R §1.4's flag with the reference's own meaning (D §5), and a backend that
silently changed the worker count would be changing a documented number to flatter itself — but it
is the number to reach for when timing the GPU path, and it is why `Backend::Auto`'s constant now
carries this table instead of G2's.

`GpuExecutor::AUTO_ELIGIBLE` therefore stays `false`. D §6.8's bar is 1.5× and the honest
measurement is 1.04–1.40×. What would move it is a device that does not share the envelope — E8's
discrete rows — not more work on this one.

## 6. Item 2: the BVH kernels, and the rule that was applied to them

The task's rule: build D §6.2's `bounded_distance` and `inside` kernels **only if** the measurement
shows R §6 at ≥ 5 % of GPU-backend wall. It does: **15.9 %** of core time, ~8 % of wall. The
trigger fires, so this section is the argument for not building them anyway, with the numbers that
make it.

What the batches look like, counted through the delegation counters this task added:

| set | `bounded_distance` | `inside` |
|---|---|---|
| synthetic_20 | 1 296 calls, 14.1 M points — **10 901 per call** | 1 480 calls, 29.6 M points — **20 000 per call** |
| pot_H | 1 674 calls, 21.3 M points — **12 712 per call** | 1 150 calls, 23.0 M points — **20 000 per call** |

So they are not too small to dispatch: 10–20 k queries per call is the size at which `icp.wgsl`
already wins. Size is not the objection. **The objection is which resource is short.**

After this task, `synthetic_20`'s stage is 13.38 s, of which the device has work outstanding for
9.06 s (68 %) and the CPU burns 78 core-s of the 134 available (58 %). R §6 is 12.45 of those 78
core-seconds. Moving it to the device takes **at most 1.2 s** off the stage — that is what its work
costs when perfectly spread over ten cores — and adds 43.7 M BVH queries to a device that has 4.3 s
of slack, is already 1.6× down on its idle throughput, and gets slower the busier the CPU beside it
is. For that to break even the kernel would have to run 43.7 M closest-point and parity queries in
under 4.3 s of a device that is two-thirds committed. E7 and G1 measured the *hash-grid* kernel —
no stack, no triangle projection, a far cheaper traversal — at 55–80 M queries/s on an **idle**
device.

So the expected outcome is between "no change" and "worse", the work is D §12's largest remaining
2c item, and the decision is to **keep both methods on the CPU executor and say why in numbers**.
Two things would change the answer and both are measurements rather than opinions: a discrete
adapter, where the device does not share the envelope (E8), or a prototype kernel measured against
`gpu-check`'s `distance` and `inside` rows, which exist and are labelled `delegated` today. The
counters that would size it are now in every run's output.

## 7. Item 4: the chunking, and the fold

Two tests in `crates/sherd-gpu/tests/adapter.rs`, each a property rather than a golden number.

**`the_coarse_kernel_chunks_past_the_dispatch_caps_and_folds_the_grid`** crosses both caps on one
batch: 400 000 poses on a sixty-point probe is 24 M point-queries, past
`coarse::MAX_POINT_QUERIES`, so the call becomes two dispatches; the first is 333 333 workgroups,
past `MAX_WORKGROUPS_PER_DIM` = 65 535, so its grid folds into two dimensions and the kernel has to
recover its pose index from `params.wg_x` (E7 §3: the shape is data, never a constant on one side).
The poses repeat with period 200, so score `p` must equal score `p % 200` — across the fold, across
the chunk boundary and across `first_pose` — and the first 200 must be the CPU executor's own bits.

**`the_icp_kernel_chunks_at_the_tdr_ceiling`** puts 600 candidates through D §6.4's 512 ceiling.
The initial poses repeat with period 100, so the first candidate of the second dispatch has a twin
in the first and must come back the same registration, which is what checks that a chunk's state
buffer, its `first` and its slice of the one staging buffer line up. The ICP grid never folds — one
workgroup is one candidate and a dispatch is capped three orders of magnitude below the
per-dimension limit — and the test says so rather than leaving it to be discovered.

Both run on this machine's adapter and skip with a printed reason where there is none.

## 8. Item 5: device memory

`--gpu-memory GB` (default D §1's 1 GB, `0` removes the bound, on `run` and `bench`), and
`sherd_gpu::device::Allocations` behind it. A batch is **reserved before it is uploaded**: each
kernel adds up the buffers it is about to create (`device_bytes`, written out buffer by buffer) and
asks for them; what does not fit is answered by the CPU executor and counted as a refusal, never
allocated anyway. The reservation is an RAII guard, so a call's bytes are released when the call
returns. The admission rule is `SlotTable`'s one level down: a request larger than the whole budget
is refused rather than admitted after everything else has been given up.

Measured peaks at the default, whole runs:

| set | peak device allocation | budget | refused |
|---|---|---|---|
| synthetic_20 | **103 MB** | 1.00 GB | 0 |
| pot_H | **21 MB** | 1.00 GB | 0 |

D §1's "slots + batches ≤ 1 GB" holds with an order of magnitude to spare, and it holds because the
batches are per-call and small, not because anything is evicting. `run` prints the line.

**And then the small cap the task asked for turned into the most interesting measurement of the
task.** `--gpu-memory` at 50 and 20 MB on `synthetic_20`, three runs each, interleaved with the
default:

| `--gpu-memory` | batches refused | matching stage | median | device outstanding |
|---|---|---|---|---|
| default, 1 GB | 0 of 326 | 12.77, 12.67, 13.33 s | **12.77 s** | 9.5–11.2 s |
| **0.05** | 17–18 | 11.79, 10.09, 10.75 s | **10.75 s** | 6.9–7.5 s |
| 0.02 | 39–47 | 11.21, 11.24, 10.83 s | 11.21 s | 5.1–5.4 s |

**Giving the device less work made the stage faster.** Refusing the seventeen largest batches — a
5 % ceiling on the device's share of the calls — took the matching stage from 12.77 s to 10.75 s,
which against the CPU backend's ~14.5 s is **1.35×**, the best figure on this collection and at the
*default* thread count. The joins, groups and poses are unchanged at every cap, because a refused
batch is answered by the reference implementation.

This is §5's envelope seen from the other side, and it says something the three size thresholds do
not. `coarse::MIN_QUERIES`, `icp::MIN_CANDIDATES` and `icp::MIN_WORK` are a **floor**: below them
the CPU is faster on that batch alone. What the table above shows is that there is also a
**ceiling** — a batch large enough that running it on the device costs the *machine* more than it
saves, because the ten cores it stalls beside are the other half of the same budget. Nothing here
acts on that: `--gpu-memory` is a memory knob and using it to split work would be using the wrong
instrument, and a measured ceiling belongs in the thresholds beside the measured floors. It is
named in §11 as the next task's, with the table it would be derived from.

**`SlotTable` still has no consumer, and this task did not give it one.** G2's open issue 6 said
residency needs the multi-pair batch of D §6.5's sketch (`pose_pair[h]`, `pair_grid[pair]`), and
that is still true: what the kernels upload per call is a *pair's* target at a *rung's* radius, not
a fragment, so there is no per-fragment object to keep resident and nothing for an LRU to evict.
The honest form of "slot LRU eviction under a small `--gpu-memory` cap" is therefore the admission
rule above, tested in `the_device_memory_budget_sends_what_it_cannot_hold_to_the_cpu`: the same
batch runs on the device under 1 GB and is refused under 1 MB, and the refused one comes back as
the CPU executor's own answer to the bit. §2's other finding is the reason not to regret this —
device-side preparation is 1.7 % of the run, so a resident set would be optimising a rounding error.

## 9. Item 6: cancellation and progress

D §5's two remaining sentences, which had never been built. `sherd_core::progress` carries
`Cancel` (an `AtomicBool` behind an `Arc`), `Progress` (`advance(stage, done, total)`) and `Watch`,
the pair of them, which `RunOptions` now holds and which defaults to neither. The checks are
**between units of work and never inside one** — a fragment in preprocessing, a pair in matching —
so a cancelled run has finished every unit it started and nothing half-built is written or cached.
The CLI wires Ctrl-C to it (`ctrlc`, the one new dependency: `std` has no signal API on any
platform); a second Ctrl-C aborts, because the first can take as long as the pair in flight.

On the GPU path the claim to check was *"Ctrl-C mid-batch leaves no device hang"*, and
`a_cancelled_gpu_run_leaves_the_device_usable` checks it the only way that means anything: the run
is cancelled **from its own progress callback**, so the moment is deterministic rather than a
sleep, and then a real 64-candidate rung goes through the same device and is asserted to land on
it. It does, and `Allocations::live()` is zero afterwards. There is nothing to unwind: a dispatch
is bounded by D §6.4's chunking, and the submitting thread retires every command buffer it
submitted before its channel closes.

## 11. What is left

1. **The envelope is the ceiling, and it is not a bug to fix.** 1.04–1.40× is what an integrated
   GPU sharing power and bandwidth with ten busy cores gives on this workload. The remaining
   headroom on *this* machine is the 4.3 s of device slack at nine threads, and §6 argues that R
   §6's kernels would spend it without buying it back. The measurement that would change the
   picture is E8's discrete rows.
2. **`--threads 6` is this machine's best GPU configuration** (11.86 s against 13.38 s at nine, and
   against the CPU backend's ~14.5 s). It is deliberately not a default. If a later phase wants
   one, the honest form is a *measured* per-machine choice — the self-test could time the stage's
   own shape rather than a bounded-NN kernel — not a constant.
3. **The size thresholds have a floor and no ceiling, and §8 measured that they need one.**
   Refusing the seventeen largest device batches of `synthetic_20` — which is what
   `--gpu-memory 0.05` does by accident — takes the matching stage from 12.77 s to 10.75 s, or
   1.35× the CPU backend at the default thread count. A ceiling beside `coarse::MIN_QUERIES` and
   `icp::MIN_CANDIDATES` is the cheapest remaining gain in the GPU path and it is a *measurement*
   task, not a design one: the crossover tables in `tests/adapter.rs` were taken on an idle device
   and would have to be retaken with the ten cores loaded, which is the condition a run is actually
   in. It must not be smuggled in through the memory flag.
4. **The multi-pair batch of D §6.5's sketch is the last structural idea that has not been tried.**
   It is what would give `SlotTable` a consumer, what would put the 1 014 delegated ICP rungs of
   `synthetic_20` (of 1 148) on the device, and what D §6.4's step numbering actually describes. It
   is also a rewrite of `matching::pair` into phases across pairs, which is the largest change the
   port has been asked for since phase 1, and it should not be started without a projection of what
   it is worth against §5's envelope.
5. **`gpu-check`'s stage-2 tail is G2's and is unchanged**, to the digit: `icp s2 t` 2.012e-1,
   `t@cloud` 1.332e-1, `rmse` 7.659e-4 on terracotta, the same four rows failing for the same
   reason. It changes no join on any development set; G2 §5 separates the ladder's share from the
   kernel's.
6. **`sherd_parity::stages::pose_gap` still reads its angle off `trace(RᵀR')`** and reports 3.6e-2°
   for a pose against itself (G2's finding 3). Untouched here; it belongs to a verification pass.
7. **The per-thread `gpu_nanos` counter is kept and is now labelled.** It is the number G2 quoted
   and it is not device time; `Occupancy` is. Both are printed, with the difference spelled out on
   the line, because a note that quoted 85.6 s of a 13.4 s stage without saying which was which is
   how this misreading started.
