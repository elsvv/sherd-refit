# Step D3 — the run, and the five native gates

*2026-09-07. Phase 1d, step D3. Branch `rust-core`.*

Every stage of R exists in the port; this step is the wire between them. `sherd_refit.pipeline.run`
becomes `sherd_core::pipeline::run`, `sherd_refit/cli.py` becomes `sherd-refit-rs run`, and the five
gates the plan states for the whole pipeline are run on the real collections rather than on fixtures.

The port assembles the terracotta exactly as R §13 requires, is byte-identical between two runs
everywhere except the wall clock, and finishes the six benchmark sets in **6 to 50 seconds** where
the reference needs **53 to 427**. On the quality table it reproduces the Python figure on three of
the six sets, beats it on one and loses two — and §5 shows, with the parity harness rather than with
an argument, that all three differences are the PMC-6/PMC-9 search difference and not a defect: on
those same three sets the port's own R §8, fed the *reference's* candidates, reproduces the
reference's assembly exactly, join for join and rejection for rejection.

### 1.1 What the run does, in the reference's order

Discovery (R §2) → preprocessing through the cache (R §3, D §5 stage 2) → the collection medians and
the 40 % warning (R §4.1) → pair enumeration with the 2.5× wall-ratio filter (R §4.1) → the optional
partner search (R §4.3) → R §5–§6 over the pairs in D §5's block order → R §8 → the optional second
pass (R §8.1) → R §9 → R §8.2's recentring → R §11's five writers. Every stage times itself into
`timings`.

**One thing in R §11.2 is wrong and the fixtures say so.** R §11.2 lists `output` among the
`timings` keys; the reference computes it *after* `json.dump` has already written the file, so
`report.json` never carries it. All eight dumps hold `preprocess`, `matching`, `assembly` and
`refine` and nothing else. The port keeps `output` out of the file for the same reason and reports
it only to the caller and the log.

### 1.2 The schedule (D §5), and what one process changes

The reference forks a process pool per stage; the port is one process with one rayon pool. The
*order* survives, because that is what fixes which fragment a worker already holds:

| regime (`n` pairs, `w` workers) | reference | port |
|---|---|---|
| `n ≤ 4w` | one process per pair, `cores/procs` threads inside it | blocks of 3×3 fragments; nested `par_iter` inside a pair fills the pool |
| `4w < n < 16w` | `w` processes, 1 thread, **no blocking** | one job per pair (`block_size = 1`) |
| `n ≥ 16w` | `w` processes, 1 thread, blocks of 3 | blocks of 3×3 fragments |

`block_size` is the reference's own rule and its middle row is the one it measured: pot H's ten
blocks over nine workers ran 688 s blocked against 505 s unblocked (`notes/2026-09-06-scale-pairs.md`
§5). Under rayon the two ends of the table need no separate code — work stealing spreads a pair's
candidates when there are few pairs and keeps a thread on each block when there are many — so the
only thing the port has to reproduce is which pairs share a job, and it does.

D §5's shared `MatchData` LRU is **not** there. A pair rebuilds one of its two fragments' arrays at
`t_pair`; R's own cost table puts that at 0.2 s against a pair's several seconds, and the gates below
are met without it. The block order is already the order an LRU would want, so it can be added later
without moving a single number.

## 3. Gate 2 — `tools/evaluate.py` on the port's outputs

Every set was run end to end by the port and scored by the reference's own evaluator, which reads
`OUT/transforms.json` and `OUT/report.json`. It read all six without a change.

| set | port fragment accuracy | Python | port precision | Python | port group | Python group |
|---|---|---|---|---|---|---|
| `pot_A` | **100.0 % (8/8)** | 87.5 % | **1.000** | 1.000 | 8 | 7 |
| `pot_B` | 88.9 % (8/9) | **100 %** | 1.000 | 1.000 | 8 | 9 |
| `pot_C` | **75.0 % (3/4)** | 75.0 % | **0.667** | 0.667\* | 3 + 2 | 5 |
| `pot_G` | **0 % (0/7)** | 0 % | 0.000 (2 joins) | — (0 joins) | 2 + 2 | none |
| `pot_H` | **36.4 % (4/11)** | 36.4 % | **0.429** | 0.429 | 7 + 2 | 8 |
| `synthetic_20` | 90.0 % (18/20) | **95 %** | **1.000** | 1.000 | 15 + 3 | 19 |

Group purity is **1.000** on every set and cross-object joins are **0**, as R §13 requires of all
sets. Summed over the six, the port places 41 of 59 ground-truth fragments correctly against the
reference's 42 — the same number to within one fragment, arrived at by a different search.

Three rows reproduce the Python table exactly (`pot_C`, `pot_G`, `pot_H`), one is better (`pot_A`)
and two are worse (`pot_B`, `synthetic_20`). Two of the six need a word of their own.

**`pot_C`'s precision column is the one R §13 calls "one draw of a coin", and it lands on the other
side here.** The port prints 0.667, which is R §13's printed value; the *current* Python — with
task T1's deterministic thickness — prints 0.500 on the same set (D2's note §6.3, measured through
the port's own R §8 on the reference's candidates, where the `assembly` row is exact). Fragment
accuracy, the number R §13 leads with and the one it calls stable, is 75.0 % on both. The port also
splits pot_C into groups of 3 and 2 where the reference makes one of 5 — the same fragments placed,
one join fewer holding them together.

**`pot_G` deserves its footnote.** R §13's gate is "0 % (ground truth interpenetrates; no join must
be accepted)". The port meets the number — 0 of 7 fragments placed correctly — and not the clause: it
accepts two pairs where the reference accepts none of its 105 candidates. Both are ground-truth
*adjacent* pairs (04–07 and 02–05) at poses 0.7°/1.05 t and 2.5°/1.20 t from the ground truth, i.e.
just outside the evaluator's 0.5 t, with `tight` 0.656 and 0.450, seams of 32.7 t and 36.7 t and
`pen` 0. On a set whose own ground truth interpenetrates, these are near-misses rather than nonsense;
they are still two joins R §13 says should not be there, and the clause is not met.

## 5. Where the port and the reference part, measured rather than argued

Two sets differ, in opposite directions. Both are the same cause, and the parity harness is what
proves it rather than a story about floating point.

### 5.1 The control: R §8 is not the difference

`sherd-refit-rs parity --stage assembly` in **native** mode runs R §8 twice. Its PMC-8 pass feeds the
port's own R §8 and the port's own surface samples (the fragment's own 20 000 at its own `t`) with
the *reference's* candidates, and compares against the reference's own assembly:

| set | `pmc8 groups` differing | `pmc8 used` | `pmc8 rejected` | `pmc8 pen` moved by | `pmc8 pose move` | status |
|---|---|---|---|---|---|---|
| `pot_A` | 0 of 2 | 0 of 6 | 0 of 10 | 0.0078 | 4.9e-14 t | **PASS** (10 checks) |
| `pot_B` | 0 of 1 | 0 of 9 | 0 of 12 | 0.000 | 4.1e-14 t | **PASS** (10 checks) |
| `synthetic_20` | 0 of 2 | 0 of 23 | 0 of 0 | 0.000 | 9.1e-14 t | **PASS** (10 checks) |

So on all three sets where the end-to-end answer differs, the port's greedy growth, its consistency
test, its penetration test and PMC-8's own sample set reproduce the reference's groups, its used
joins in order, its rejections *with the reference's own English sentences and their measured
numbers*, and its poses to 1e-13 t. Everything below R §8 is exonerated. What is left is the
candidate list R §8 is given.

### 5.2 `pot_A`: the port misses a decoy the reference finds

Both assemblies take the same six joins in the same order. The reference then leaves `Piece_02`
unplaced and the port places it. The best candidate of every `Piece_02` pair, both sides:

| pair | reference | port |
|---|---|---|
| 02–05 | score **32.87**, tight 0.795, seam 41.3 t, accepted | score **0.00** — the port's search never produced this pose |
| 02–08 | score 19.99, tight 0.645, accepted | score 19.83, tight 0.647, accepted |

R §8 takes each pair's best candidate in score order. The reference's strongest `Piece_02` join is
02–05, and it refuses it: *"penetrates Pot_A_Piece_04_Mesh (0.007)"*, against a limit of 0.005. Having
spent the pair, it then refuses 02–08 as *"inconsistent with stronger join 02–05"* and `Piece_02` is
never placed. The port's search never found that 02–05 pose at all, so its strongest `Piece_02` join
*is* 02–08 — the correct one — and it takes it. **7/8 → 8/8**, precision still 1.000.

### 5.3 `pot_B`: a 0.7° difference in a neighbour costs a fragment

The port leaves `Piece_09` unplaced. All three of its joins were accepted by R §6.5 and refused by
R §8:

```
07–09  score 29.86  tight 0.705  pen 0.0000   ->  penetrates Pot_B_Piece_06_Mesh (0.024)
01–09  score 26.58  tight 0.767  pen 0.0000   ->  penetrates Pot_B_Piece_06_Mesh (0.034)
06–09  score 21.09                            ->  inconsistent with stronger join 07–09
```

The join itself is right: `evaluate.py` scores the port's 07–09 pose at **0.7° / 0.15 t** from the
ground truth, and the port's pose for it is **0.16° / 0.29 t** from the *reference's* own 07–09 pose.
What differs is the fragment it is measured against. `Piece_06` is placed by 04–06, and there the two
searches are **0.72° / 0.62 t** apart; against the ground truth the port's `Piece_06` sits 0.58° / 1.24 t
off and the reference's 0.54° / 1.15 t. That is the whole of it: a hard threshold at 0.005 of 20 000
surface samples, applied to a fragment placed a fraction of a degree differently. §5.1's control is
the proof — hand the port's own penetration test the reference's poses and it accepts 07–09 and
reproduces the reference's nine joins exactly.

### 5.4 `synthetic_20`: two joins on the threshold, one fragment and one group

The port uses 19 joins where the reference uses 23, and its rejections name the same test:

```
010–015  score 37.7  ->  penetrates frag_002 (0.012)
002–015  score 31.8  ->  penetrates frag_010 (0.006)
016–019  score 19.7  ->  penetrates frag_000 (0.012)
005–007  score 21.8  ->  inconsistent with the assembled poses (0.5 deg, 0.77 t)
```

`frag_015`'s two joins are both refused and it stays unplaced (**19/20 → 18/20**); 016–019 is the
join the reference uses to close its group of 19, and without it the port's assembly is 15 + 3. The
narrowest of the four is 002–015 at `pen = 0.006` against `max_pen = 0.005` — **twenty of twenty
thousand surface samples**. Every one of the four poses is scored `ok` by `evaluate.py`, so the port's
precision stays 1.000: it loses recall here, never correctness.

### 5.5 What this says about the two implementations

PMC-6 (numpy's unstable `argsort` in R §5.3's and R §5.4's ranking, against the port's stable sort)
and PMC-9 (numpy's PCG64 against the port's ChaCha8) mean the two implementations *search different
poses*, which C1 measured at up to 43.6 % different survivors of R §5.3's suppression and C3
restated at the candidate level. R §6.5 and R §8 are thresholds on the output of that search. The
sets where the thresholds are not close — the terracotta, `pot_C`, `pot_H` — come out identical; the
sets where a fragment sits on a threshold flip, and they flip in both directions. R §13 says the same
thing about `pot_C`'s precision in its own words: "one draw of a coin".

The right gate for those cases is the parity table, which is exact, and it passes.
