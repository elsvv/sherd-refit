# P0 — the parity harness on the Python side

**Date:** 2026-09-06. Branch `rust-core`. Plan row P0 of
`docs/superpowers/plans/2026-09-06-rust-core-phase0-1a.md`; design §10.1, §10.2, §10.4 (D);
algorithm reference (R) for the stage boundaries and the RNG draw order.

The Rust core has to be judged stage by stage rather than only on its final poses, and for that
the reference has to be able to show its work: what went into each stage and what came out, with
the dtypes intact, so that the port can be handed one stage's input and its output compared. This
note records what the sink writes, what it costs, and what was measured about it.

Three pieces:

| piece | what it is |
|---|---|
| `sherd_refit/fixture.py` | the sink; off unless `SHERD_REFIT_FIXTURES=DIR` is set |
| `tools/dump_fixtures.py INPUT_DIR OUT_DIR` | one pipeline run with the sink on, plus a hashed `manifest.json`; `--verify-determinism` runs it twice and diffs |
| `tools/compare_fixtures.py REF CAND` | the D §10.2 tolerance table, as a per-stage pass/fail report with an exit status |

`fixtures/slab/` is the one dump small enough to commit (the synthetic slab pair of
`tests/test_synthetic.py`, 163 files, 17.8 MB: the dump, the two input meshes and their ground
truth). Everything else lives in `output/fixtures/` and stays out of git.

Two of those files nearly did not make it. The repository ignores `input/` and `out*/` *anywhere*
in the tree, so `fixtures/slab/input/` and `fixtures/slab/dump/outputs/` — the collection the dump
was made from and the expected `transforms.json` / `report.json` — were silently left out of the
first fixture commit, and a fresh `git archive HEAD` failed six of `tests/test_fixtures.py` and
errored two more while the working tree passed all of them. `.gitignore` now re-includes
`fixtures/**/input/` and `fixtures/**/outputs/`. Anything added under `fixtures/` later is worth
checking the same way: extract HEAD into an empty directory and run the tests there, not in the
tree that generated it.

## 1. How the sink works

`SHERD_REFIT_FIXTURES=DIR` switches it on and is inherited by the worker processes, so one
variable covers preprocessing, matching, assembly and refinement. With it unset every call
returns immediately; `pytest -q` passes unchanged (30 tests before this task, 54 after) and
`tests/test_fixtures.py::test_the_sink_does_not_change_the_result` asserts that a run with the
sink on writes the same `report.json` as a run without.

Each call site is a `put(key, value, group)`. `key` becomes the file name (`.npy` for an array,
written with its own dtype and no compression; `.json` with sorted keys otherwise) inside the
*scope* directory of whatever owns the stage — a fragment, a pair, the assembly. `group` is one
of thirteen tags, and `SHERD_REFIT_FIXTURES_LEVEL` picks which tags are written:

| level | groups | use |
|---|---|---|
| `full` (default) | all | small collections; everything, including the cleaned original mesh |
| `slim` | all but `orig` | the original mesh is by far the largest array and the port can reload it from the file |
| `min` | `counts mesh seg_final md result assembly refine outputs` | D §10.1's reduced set for very large collections |

Three properties took design work:

* **Determinism.** Files go to a temporary name and are renamed into place, so two worker
  processes writing the same deduplicated array cannot interleave and a reader never sees a
  partial file. The per-candidate arrays of stage 2 are produced by a thread pool, so they are
  collected in memory by job index (`fixture.Trace`) and written in job order by the thread that
  owns the pair — the file set never depends on the thread schedule. `report.json`'s wall-clock
  timings are blanked in the dump. `manifest.json` is built afterwards by walking the tree,
  because no single process sees all of it.
* **Size.** A pair is matched at `t = min(t_A, t_B)`, so the thicker fragment rebuilds its match
  arrays; dumping those per pair would make a fixture grow with the square of the collection.
  They are dumped per `(fragment, t, surface_points)` instead, under
  `fragments/<name>/md_t/t<t>_sp<n>/`, and the pair records which ones it used in `md_used.json`.
* **Completeness.** Preprocessing ignores its `.npz` cache while the sink is on, so a dump is
  never missing a fragment because an earlier run had already computed it.

## 3. Determinism

`tools/dump_fixtures.py --verify-determinism` dumps twice and compares every SHA-256.

| set | files | result |
|---|---|---|
| slab | 158 | byte-identical |
| terracotta | 444 | byte-identical |
| pot_G | 1129 | byte-identical |
| terracotta, `--level slim`, re-checked at `5ad7941` | 436 | byte-identical |

The check found the one place where the reference is **not** bit-reproducible: Open3D's
point-to-plane ICP sums its normal equations with an OpenMP reduction whose order follows the
thread schedule, so the full-resolution refinement (R §9) — the only ICP that runs in the parent
process with more than one OpenMP thread — moves by about 1e-15 between two runs of the same
input. R §10's claim that two runs give a byte-identical `report.json` holds, because
`report.json` carries no refined pose; `transforms.json` does. `tools/dump_fixtures.py` therefore
sets `OMP_NUM_THREADS=1` before Open3D is imported (`--omp-threads N` to change it), which makes
the whole dump reproducible. Everything upstream of the refinement already runs single-threaded
inside the matching workers and was reproducible as it stood.

`tests/test_fixtures.py` re-checks this in-process with the refinement switched off, because a
process that has already used the OpenMP pool cannot reconfigure it.

## 4. The comparison tool

`tools/compare_fixtures.py REF CAND [--mode injected|native]` walks thirteen stages and prints
one row each: quantities compared, quantities failed, and the worst one as a fraction of its
tolerance, so a passing run still says how much headroom is left. Exit status 1 on any violation.

```
stage         checks  failed  worst/tol  status
load              67       0       0.00  PASS
...
stage1         41305       0       0.00  PASS
```

The tolerances are D §10.2 verbatim. Notes on how they are measured:

* **Poses** are compared as the rotation angle and the translation of the relative transform
  `T_ref⁻¹ T_cand`, the translation in wall thicknesses (`t` from the pair's `scales.json`, the
  collection median for assembly and outputs). Comparing raw translation columns would charge a
  pose for a rotation about a distant origin.
* **Stage-1 and stage-2 candidates are matched by the hypothesis they came from**, not by
  position: `nms1.kept` gives the hypothesis id, `nms2.kept` gives the position in the stage-1
  arrays. A candidate list in a different order is still compared like with like.
* **Segmentation agreement** is the area-weighted fraction of faces labelled the same when the
  two working meshes are the same tessellation, and otherwise 200 000 area-weighted samples on
  the reference mesh labelled by their nearest face centroid on each mesh (D §10.2's rule). Both
  paths are exercised by the tests; the sampled one takes about 0.2 s per fragment.
* **Breakline** in injected mode is the symmetric Hausdorff distance in `t` plus the dihedral of
  each reference point against its nearest candidate point; in native mode the 99th percentile of
  the same distances and a two-sample KS statistic on the dihedral distributions.
* `coarse`, `stage1` and `stage2` are injected-mode only, as in D §10.2; in native mode they
  report SKIP.

`tests/test_fixtures.py` checks the tool against the committed slab dump: it passes on two copies
in both modes, and fails, thirteen times over, on a copy with exactly one file perturbed the way
each stage's tolerance is there to catch — a face count moved by seven, a thickness by 10 %, an
area by 2 %, a fifth of the segmentation labels flipped, the breakline displaced by 0.3, five
hypotheses dropped, a coarse score raised by 0.05, a stage-1 score by 0.05, `tight` by 0.05, an
accepted flag cleared, a join removed from the assembly, a refined pose shifted by two units, a
transform shifted by two units.

The assemblies are the ones the reference is expected to produce: the terracotta joins are
exactly `{021–094, 094–104}` with 007 unplaced and both penetrations 0, which is R §13's gate for
that set stated in full; pot A 7 of 8 in one group, pot B all 9, pot G no join at all (its ground

synthetic 20 19 of 20. The percentage gates of R §13 are computed by `tools/evaluate.py` against
the ground-truth poses and were not re-run here; these are the group structures the fixtures
record.

**One R §13 number is stale.** It gives the 094–104 seam as ≈ 11–12 t, taken from
`2026-09-05-test-set-result.md`, which measured 11.3 t with tight 0.42 / 0.28. At HEAD the join
scores seam 10.7 t with tight 0.58 / 0.59 — the two commits after that note (`991ff87`, a quarter
of the hypotheses and a tenth of the candidates; `ca59c6a`, the coarse stage-2 ICPs on six
thousand points) moved it. The join itself, its acceptance and every other terracotta gate are
unchanged. A port matching the fixture rather than R §13's prose is right; worth knowing before
the V step chases it.

Wall-clock on this M2 Pro with `--workers 4` and `OMP_NUM_THREADS=1`: terracotta 63 s, pot_C 57 s,
pot_G 43 s, pot_A 141 s, pot_B 155 s, pot_H 140 s, synthetic_20 515 s.

Sizes came out larger than D §10.1 guessed (terracotta 232 MB against ≈ 40 MB, synthetic 20
1.39 GB at `slim` against ≈ 350 MB). Two things dominate and neither was in the estimate: the
cleaned original mesh at float64/int64 (156 MB of the terracotta's 232 MB, because those scans
carry 0.7–1.3 M faces each — `--level slim` drops it), and the per-pair hypothesis arrays, three
int64/float64 vectors of `n_h` ≈ 16k–150k entries, which is 0.4–3.6 MB per pair and is what makes
synthetic 20's 190 pairs cost more than a gigabyte. For `mixed_all` and `synthetic_170` use
`--level min`, which drops both along with the segmentation intermediates, as D §10.1 already
prescribes for those sets.

## 6. Regenerating

```
python tools/dump_fixtures.py input/test_fragments_1/fragments output/fixtures/terracotta --workers 4 --force
python tools/dump_fixtures.py input/sfspp/pot_A               output/fixtures/pot_A       --workers 4 --force
python tools/dump_fixtures.py input/synthetic_pingsdorf_20/fragments output/fixtures/synthetic_20 --workers 4 --force --level slim
python tools/make_slab.py fixtures/slab/input
python tools/dump_fixtures.py fixtures/slab/input fixtures/slab/dump --force --verify-determinism && rm -rf fixtures/slab/dump/_run
```

Each `manifest.json` records the commit it came from and whether the tree was dirty; the sets
above were dumped at `e9a8ccb`, `eeb3c8d` and `fd5f67e`, whichever happened to be HEAD while the
other phase-0 agents were committing their notes. That is safe to compare across: the only commit
that has touched `sherd_refit/` since `9d4b9d3` — the reference point the plan names — is the
fixture sink itself, which does nothing at all when `SHERD_REFIT_FIXTURES` is unset
(`git log 9d4b9d3..HEAD -- sherd_refit/`).
