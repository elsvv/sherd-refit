# sherd-refit — автоматическая сборка 3D-сканов керамических фрагментов

## Что это и для чего

`sherd_refit` — консольная программа, которая берёт папку со сканами фрагментов одного разбитого
керамического предмета и подбирает наиболее вероятную сборку: сопоставляет фрагменты по
поверхностям излома и выдаёт для каждого жёсткое преобразование (поворот + перенос).
Работает только на процессоре, без видеокарты и без графического интерфейса, на macOS и Linux.
Вход — папка с файлами PLY/OBJ/STL (также читается OFF); выход — матрицы преобразований,
меши в найденных позициях, склеенная модель для каждой собранной группы, картинки-превью и
отчёт `report.md`, где по каждому стыку видно, почему он принят или отклонён.

## Установка

Нужен Python 3.10–3.12 (верхняя граница из-за готовых сборок open3d).

```bash
uv venv --python 3.12 .venv && source .venv/bin/activate && uv pip install -e .
```

Без `uv`:

```bash
python3.12 -m venv .venv && source .venv/bin/activate && pip install -e .
```

Ставятся numpy, scipy, open3d, pillow и сама команда `sherd_refit`.

Требования к данным:

- Меши должны быть замкнутыми или почти замкнутыми. Из каждого файла берётся наибольшая
  связная компонента; если после этого меш всё равно не замкнут, для него отключается проверка
  на взаимное проникновение, и в отчёте это отмечено (`watertight = False`).
- Все фрагменты в одних и тех же единицах и примерно одного масштаба. Толщина стенки `t`
  считается для каждого фрагмента отдельно, и пара сопоставляется по своей толщине, поэтому
  коллекция из горшков с разной стенкой — нормальный вход. Медиана по коллекции остаётся только
  для отчёта: фрагмент, у которого толщина отличается от неё больше чем на 40 %, помечается
  пометкой **(differs)**.
- Поперёк стенки должно укладываться хотя бы 4–5 рёбер меша. Меньше — и излом не разрешается
  сеткой; в отчёте это видно в столбце `edges per t`.
- В папке должно быть не меньше двух файлов.
- Цвет не обязателен. При сопоставлении он не используется, но переносится в выходные меши.

## Быстрый старт

```bash
sherd-refit run input/test_fragments_1/fragments --out output/test_fragments_1
```

В папке `--out` появляется:

| файл | что это |
|---|---|
| `report.md` | отчёт для чтения человеком: фрагменты, группы, принятые стыки и их оценки |
| `report.json` | то же самое в машинном виде плюс все кандидаты по каждой паре |
| `transforms.json` | матрица 4x4 на фрагмент, номер группы, флаг `placed`, толщина стенки, параметры запуска |
| `placed/<имя>.ply` | исходный меш в полном разрешении, уже сдвинутый в найденную позицию |
| `assembly_<k>.ply` | один склеенный меш на каждую группу из двух и более фрагментов |
| `preview_<k>.png` | четыре вида собранной группы, каждый фрагмент своим цветом (подпись сверху) |
| `preview_segmentation.png` | все фрагменты в ряд, красным — распознанная поверхность излома |
| `cache/<имя>.npz` | результат предобработки одного фрагмента, чтобы повторный запуск не считал заново |

Смотреть результат: `assembly_0.ply` и файлы из `placed/` открываются любым просмотрщиком
мешей — MeshLab, Blender, CloudCompare. Просмотрщик macOS Preview для PLY ненадёжен, цвета
вершин он показывает не всегда, поэтому проверять сборку лучше в MeshLab или Blender.
Для быстрой оценки достаточно PNG-превью: цвета там служебные (серый, оранжевый, синий и т. д.),
это не цвет самой керамики.

### Как читать таблицу стыков в report.md

Все расстояния выражены в толщинах стенки `t` (на тестовом наборе `t` = 38.9 единиц),
поэтому пороги не зависят от масштаба сканов.

**Толщина стенки и разрешение сетки.** Каждый порог расстояния задан сразу в двух единицах и
равен `max(k·t, m·res)`. Первое слагаемое, `k·t`, делает пайплайн независимым от масштаба скана.
Второе, `m·res`, где `res` — медианная длина ребра рабочего меша, не даёт требовать точности,
которой в сетке нет: `m` — это счёт рёбер. На толстостенной терракоте из `test_fragments_1`
поперёк стенки укладывается 17 рёбер (`res` = 0.058 `t`), и там во всех порогах побеждает первое
слагаемое — множители подобраны именно так, чтобы на этом наборе ничего не изменилось. На
тонкостенном горшке поперёк стенки бывает 4–6 рёбер, и включается второе: например, порог
плотного прилегания `0.01 t` там равен 0.035 мм, то есть много меньше одного треугольника.

Для пары фрагментов `t` = меньшая из двух толщин (венчик и утолщённый край завышают оценку,
стенка — это меньшее из двух), а `res` = большая из двух: точность пары ограничивает более грубая
сетка. В таблицах отчёта у каждого кандидата выписаны обе величины, по которым его судили:
`tight at (t)` и `gap limit (t)`.

| столбец | что означает | как читать |
|---|---|---|
| `score` | `seam` × `tight`, только для сортировки | больше — надёжнее |
| `seam (t)` | длина общего шва вдоль линии излома, в толщинах стенки | принимается от 3; настоящие стыки на тестовом наборе дают 11 и 21 |
| `tight A/B` | доля точек излома, прилегающих к поверхности излома соседа плотнее чем `tight at`, отдельно для каждого фрагмента | решение принимается по меньшему из двух; порог 0.25 |
| `tight at (t)` | на каком расстоянии для этой пары считалось прилегание | `max(0.01 t, 0.15 res)` |
| `gap (t)` | медианный зазор между обращёнными друг к другу поверхностями излома | сравнивается со столбцом `gap limit` |
| `gap limit (t)` | предел зазора для этой пары | `max(0.03 t, 0.45 res)` |
| `contact (t²)` | площадь фактического контакта в квадратах толщины | в порогах не участвует, показывает, насколько крупный стык |
| `shell cont.` | средняя высота уступа внешней поверхности поперёк шва, в `t` | меньше — глаже переход; в порогах не участвует |
| `normal agr.` | согласованность нормалей внешней поверхности по обе стороны шва | 1.0 — поверхность продолжается гладко, порог 0.8 |
| `penetration` | доля точек поверхности, ушедших внутрь соседа глубже 0.06 t | порог 0.005; **0.0000 значит одно из двух**: проникновения не нашлось — или его нельзя было измерить, потому что меш одного из фрагментов не замкнут (столбец `watertight` в `## Fragments`). Во втором случае стык не может попасть в полосу confirmed ни при каком пороге, и в `report.md` у него написано `pen: penetration not measurable, a fragment is not watertight` |

Если включён `--early-reject-tight` (по умолчанию выключен) и у кандидата в столбце
`normal agr.` стоит `-1.00`, а `penetration` равен нулю, значит он был отсеян рано: плотность
прилегания оказалась настолько мала, что считать проникновение и непрерывность уже не имело
смысла. В `report.json` у такого кандидата стоит `partial = 1`.

Кроме принятых стыков в отчёте есть раздел **Best candidate per pair** — лучший кандидат по
каждой паре фрагментов, включая отклонённые. По нему видно, насколько ложные варианты
отстают от настоящих. Раздел **Accepted joins not used** перечисляет стыки, прошедшие пороги,
но отвергнутые при сборке (например, из-за проникновения в уже поставленный фрагмент).

## Как это работает

1. **Предобработка.** Меш прореживается до 200 000 граней (рабочая копия; оригинал сохраняется
   для вывода и финальной доводки) и слегка сглаживается. Толщина стенки `t` оценивается лучами,
   пущенными внутрь от **каждой** грани исходного меша (при более чем 300 000 граней — от
   подмножества с фиксированным шагом): берётся самое частое расстояние до противоположной
   стенки. Оценка детерминированная и от seed не зависит. Все пороги дальше выражены в `t`,
   поэтому пайплайн не зависит от масштаба.
2. **Разделение на внешнюю поверхность и излом.** Из каждой грани внутрь пускается конус из семи
   лучей. Если они попадают в противоположную стенку на расстоянии 0.5–1.8 `t` и с изнанки,
   грань относится к целой поверхности. Всё остальное — излом. Затем результат чистится
   фильтром большинства, мелкие островки убираются, а граница уточняется.
3. **Линии излома (breaklines).** Рёбра между целой гранью и гранью излома дают линию слома.
   В каждой её точке строится локальный репер из усреднённой нормали внешней поверхности и
   нормали излома. Двугранный угол между ними обычно 40–100°.
   Обе нормали усредняются **не по всей окрестности точки, а по кольцу** от `0.15 t` до `0.60 t`
   (поля `macro_inner` и `macro_outer` в `Params`, флага командной строки у них нет). Причина в самом ребре
   слома: на реальных черепках оно окатано, а рабочий меш ещё и сглажен, поэтому грани у самой
   линии заваливаются друг к другу и тянут обе макронормали навстречу. Замерено на парах
   фрагментов, поставленных в эталонные позиции: сумма двугранных углов настоящей пары
   получалась 142° вместо 180°, то есть верные пары рамок лежали на самом краю допуска и
   примерно половина их отбрасывалась ещё до оценки. С кольцом сумма равна 179 ± 4°.
4. **Гипотезы позиций.** Каждая пара точек линии излома (одна на фрагменте A, одна на B) с
   дополняющими друг друга двугранными углами задаёт одно жёсткое преобразование. Таких гипотез
   на пару десятки тысяч; они быстро отсеиваются по тому, сколько точек линии слома B легло на
   линию слома A.
5. **Многоступенчатый ICP.** Выжившие гипотезы уточняются: сначала ICP по линиям излома, затем
   по точкам излома вместе с приграничной полосой внешней поверхности, затем только по излому,
   со всё меньшим радиусом поиска. Кандидаты одной пары считаются в несколько потоков.
6. **Проверка.** Каждый кандидат проверяется по плотности прилегания, зазору, длине шва,
   непрерывности внешней поверхности и отсутствию взаимного проникновения. Стык принимается,
   только если пройдены все пять порогов.
7. **Глобальная сборка.** Принятые стыки сортируются по надёжности. Группа наращивается жадно:
   каждый новый фрагмент проверяется на проникновение во все уже поставленные, а если он связан
   с группой несколькими стыками, они должны давать согласованную позицию (расхождение не больше
   10° и 0.5 `t`). Когда группу нарастить нечем, начинается новая. Фрагменты без принятых стыков
   остаются несобранными: инструмент никогда не приставляет их силой.
8. **Доводка на полном разрешении.** Для каждого принятого стыка ICP повторяется на вершинах
   излома исходных, непрореженных мешей, что снимает погрешность прореживания и сглаживания.

Метод относится к семейству сопоставления по поверхностям излома (Huang et al., 2006), где
линии слома работают дешёвым генератором позиций. Подход Structure-from-Sherds, опирающийся на
ось вращения сосуда, для первого тестового набора не годится: предмет не является телом
вращения, оценка оси бессмысленна, и сборка получалась неверной.

## Параметры CLI

```
sherd-refit run INPUT_DIR --out OUT_DIR [опции]
sherd-refit segment INPUT_DIR --out OUT_DIR [--target-faces N] [--workers N] [-v]
```

| флаг | по умолчанию | когда менять |
|---|---|---|
| `--out` | обязателен | папка для результатов; в неё же кладётся кэш |
| `--target-faces` | `200000` | верхний предел граней рабочего меша. Фактический бюджет выбирается автоматически: ~600 граней на t² площади (около 12 рёбер на толщину стенки), но не меньше 50000 и не больше этого предела. Для тонкостенной керамики с большими фрагментами поднимайте предел (300000–400000) |
| `--workers` | число ядер минус 1 | уменьшайте при нехватке памяти: каждый процесс держит два фрагмента целиком |
| `--threads` | число ядер, делённое на число процессов | сколько потоков внутри одного процесса сопоставления. Потоки считают кандидатов одной пары параллельно; по умолчанию процессы × потоки ≈ число ядер. Ставьте 1, если хотите ровно один поток на пару |
| `--candidates` | `10` | сколько кандидатов на пару доводится полным ICP. Это главная статья расходов пары. Измерено на горшках A, B, C, H и `synthetic_pingsdorf_20`: верная поза после первой стадии оказывается на месте 0 в медиане и не ниже 6-го на всех наборах, поэтому 10 хватает с запасом (прежнее значение 40 стоило вчетверо дороже и ничего не добавляло). Поднимайте до 20–40 на трудных наборах, время растёт линейно |
| `--stage1` | `250` | сколько гипотез доводится по линиям излома. Верная поза в грубом ранжировании лежит не ниже 150-го места в 78–92 % случаев; поднимать вместе с `--candidates` |
| `--brk-voxel` | `0.5` | в толщинах стенки: воксель, до которого прореживается линия излома перед подбором пар рамок. Число гипотез растёт как обратный квадрат этой величины. При 1/3 (прежнее значение) на горшке A выходит 390 тысяч гипотез на пару и 10.2 c процессорного времени, при 0.5 — 177 тысяч и 5.6 c, и ни одного потерянного стыка |
| `--dihedral-tol` | `25` | в градусах: допуск на \|dih_A + dih_B − 180\| при отборе пар рамок. После починки макронормалей (см. ниже) сумма двусторонних углов настоящей пары лежит на 179 ± 4 градусах, и 25 градусов оставляют 97.6 % совпадающих точек против 40 градусов прежде |
| `--min-tight` | `0.25` | минимальная доля плотного прилегания; снизьте до 0.20 для сработанных, окатанных краёв излома |
| `--max-gap` | `0.03` | множитель `k` для максимального зазора; фактический предел пары — `max(0.03 t, 0.45 res)`. Повышайте, если известно, что края обиты |
| `--thick-ratio` | `2.5` | пара, у которой толщины стенок различаются больше чем в это число раз, не сопоставляется вовсе. Это только отсев; прежнее значение 1.5 отбрасывало настоящие стыки с венчиком (на горшках A и B — по 6 пар из 15) |
| `--screen-top-k` | `0` (выключено) | предварительный отбор партнёров: сколько кандидатов на фрагмент оставить перед сопоставлением. Отбор — это дешёвая (0.17 c процессорного времени на пару) грубая стадия по линиям излома на прореженной выборке; на коллекции из 164 фрагментов он сокращает 12 589 пар до 1 950 при K = 15 и режет время сопоставления в разы. **Он теряет настоящие стыки, и потому выключен по умолчанию:** на `mixed_all` при K = 15 остаётся 47 % соседних пар из эталона, при K = 30 — 64 %, на синтетическом наборе из 170 фрагментов ещё меньше. Включайте на коллекциях, где полный перебор не укладывается во время; числа и объяснение, почему дешёвый отбор на этих данных не работает лучше, — в `docs/superpowers/notes/2026-09-06-scale-pairs.md` |
| `--screen-points` | `150` | сколько точек линии излома берётся на фрагмент при отборе. Стоимость растёт как квадрат этого числа; 350 точек стоят втрое дороже и не меняют результат отбора |
| `--screen-min-pairs` | `200` | ниже этого числа пар отбор не запускается вовсе, даже если `--screen-top-k` задан. Все эталонные наборы (терракота, горшки A–J, `synthetic_pingsdorf_20`) остаются ниже порога |
| `--max-pen` | `0.005` | допустимая доля проникновения; ослаблять почти никогда не нужно |
| `--min-seam` | `3.0` | минимальная длина шва в `t`; снизьте, если фрагменты мелкие и стыки короткие |
| `--stage1-floor` | `0` (выключено) | если лучшая оценка пары по линиям излома после первой стадии ниже этого порога, вторая стадия для неё не запускается вовсе: пара сохраняет свою позу, помечается в отчёте как `partial` и никогда не принимается. Механизм точный и бесплатный, когда выключен, но **безопасного порога на этих данных нет**: у соседних пар медиана оценки 0.21–0.25, у остальных 0.19–0.22, и порог, отсекающий половину пар, стоит 10–40 % настоящих соседей. Числа в `docs/superpowers/notes/2026-09-06-scale-pairs.md` |
| `--second-pass-top` | `0` (выключено) | сколько лучших партнёров каждого несобранного фрагмента пересчитать вторым проходом с увеличенным бюджетом (`--second-pass-stage1`, `--second-pass-candidates`). Первый проход намеренно дешёвый; второй тратит освободившееся время только там, где сборка ничего не нашла |
| `--second-pass-stage1` | `400` | сколько гипотез доводится во втором проходе |
| `--second-pass-candidates` | `40` | сколько кандидатов доводится полным ICP во втором проходе |
| `--early-reject-tight` | `0` (выключено) | если больше нуля, кандидаты с плотностью прилегания ниже этого значения (замер сразу после ICP по излому с приграничной полосой) дальше не доводятся: пропускаются два последних ICP, проверка проникновения и непрерывности. Такой кандидат помечен в `report.json` как `partial = 1`, у него `penetration = 0` и `normal agr. = -1` (не считались), и он никогда не принимается. **Выключено по умолчанию:** на тестовом наборе плотность прилегания успевает вырасти ещё на 0.09 за оставшиеся два ICP, поэтому безопасный порог экономит около 7 % времени сопоставления. Включайте (0.10 и не выше), только если готовы к этому размену |
| `--margin-points` | `6000` | сколько точек приграничной полосы внешней поверхности берётся на фрагмент для ICP и проверки непрерывности. Это главный источник ускорения: полоса — это 13 000 из 30 000 точек, и именно она определяет стоимость ICP. На тестовом наборе оценки настоящих стыков меняются меньше, чем от смены зерна выборки. `0` — не прореживать вовсе |
| `--surface-points` | `20000` | сколько точек берётся по всей поверхности фрагмента. На них считается проникновение и из них выделяется приграничная полоса |
| `--frac-density` | `150` | сколько точек берётся на каждый `t²` площади излома (не меньше 5000 и не больше 12000 на фрагмент). Плотность задана в `t²`, а не числом на фрагмент, чтобы крупный черепок описывался так же подробно, как мелкий. На сами оценки число точек почти не влияет — оно кормит ICP: на 50 точках вместо 150 горшок A собирается на 5 фрагментов из 8 вместо 7. Верхняя граница держит стоимость ICP в узде |
| `--no-preview` | выкл. | не рисовать PNG, экономит время на больших наборах |
| `--no-refine` | выкл. | пропустить доводку на полном разрешении |
| `--no-meshes` | выкл. | не писать меши, только отчёт и матрицы; удобно для быстрой проверки параметров |
| `-v`, `--verbose` | выкл. | подробный лог по каждой паре |

Подкоманда `sherd-refit segment` выполняет только предобработку и сегментацию: пишет кэш и
`preview_segmentation.png`, ничего не сопоставляя. Это самый быстрый способ проверить, что
излом распознан правильно.

Кэш в `<out>/cache` хранит бюджет граней, версию формата и дату файла скана; при изменении
любого из них фрагмент пересчитывается автоматически. Удалять папку вручную не нужно.

## Ограничения и что делать, если не собралось

- **Сначала откройте `preview_segmentation.png`.** Красным показана распознанная поверхность
  излома. Если излом не красный или красным залито пол-фрагмента, сегментация не удалась, и
  ничего дальше по цепочке работать не может. Проверять сегментацию отдельно:
  `sherd-refit segment INPUT_DIR --out OUT_DIR`.
- **Сработанные, окатанные или обитые края излома** снижают плотность прилегания. Если в таблице
  Best candidate per pair видна пара с длинным швом и правдоподобной геометрией, но `tight` около
  0.2, попробуйте `--min-tight 0.2`, при необходимости вместе с `--max-gap 0.08`.
- **Тонкие фрагменты.** Если поперёк стенки укладывается меньше 15 рёбер, пороги переходят на
  второе слагаемое формулы `max(k·t, m·res)` и становятся мягче: это не настройка, а признание
  того, что более точного ответа в сетке нет. Что происходит, видно по столбцам `edges per t`,
  `tight at` и `gap limit` в `report.md`. Если рёбер меньше четырёх, излом не разрешается сеткой
  вовсе, и помочь может только более подробный скан: `--target-faces` тут бесполезен, он лишь
  ограничивает прореживание сверху.
- **Фрагменты от разных предметов**, попавшие в одну папку, обычно остаются несобранными или
  образуют отдельные группы — это нормальный исход, а не ошибка. Но **гарантии здесь нет, и на
  настоящей смешанной коллекции она нарушалась**: на восьми наборах разработки (в том числе на
  `mixed_ABG` — три горшка, 24 фрагмента) межобъектных стыков в полосе confirmed ноль при всех
  пяти сидах и чистота групп 1.000, а на приёмочной коллекции из десяти горшков (`mixed_all`, 164
  черепка) на сиде 1 таких стыков **три**, и чистота групп падает до 0.930. Все три склеивают
  горшок E с горшком I: у них совпадают толщина стенки и радиус кривизны, а признака, который
  различал бы их лучше AUC 0.800, измерение M1 не нашло. Что с этим делать за столом — в разделе
  «Настоящая коллекция: чего ждать от прогона».
- **Инструмент никогда не собирает через силу.** Если ни один стык не прошёл пороги, в отчёте
  будет строка «not assembled (no confident join)», и все фрагменты останутся на месте.
- **Незамкнутые меши** лишаются проверки на проникновение: R §6.4 на открытом меше не считается,
  признак `watertight` в отчёте равен `False`, а `penetration` печатается нулём, потому что вопрос
  был **отклонён**, а не отвечен. Последствие с задачи G — не «ложный стык отсеять сложнее», а
  прямое: **такая пара никогда не попадает в полосу confirmed**, с причиной
  `pen: penetration not measurable, a fragment is not watertight`; она остаётся в `Probable joins`,
  и решает реставратор. На наборах разработки это 3 фрагмента `pot_B` из 9 и 1 из 7 у `pot_C`; на
  приёмочной коллекции из десяти горшков — 5 черепков из 164 и 16 из 288 настоящих смежных пар
  (5.6 %).
- **Трудный набор.** Поднимите `--candidates` и `--stage1`, это увеличивает шанс, что верная
  позиция доживёт до проверки, ценой пропорционального роста времени.

## Rust-ядро (в разработке)

Параллельно с Python-версией в этом же репозитории собирается нативное ядро на Rust: тот же
алгоритм, без Open3D и с прицелом на GPU. На Python-версию оно пока никак не влияет —
разработка идёт в ветке `rust-core`.

### Ядро на Rust — теперь эталон алгоритма

**Решение задачи H4 (2026-09-09, аудит §C.1; D §13, вопрос 7).** Предполагалось, что Rust станет
эталоном в конце фазы 3a — после `pyo3`. Так не вышло: пункт 2 дорожной карты (поиск партнёров по
сигнатурам линии излома) упёрся в геометрический потолок — один шов составляет 5–22 % линии излома
фрагмента, — полный перебор пар остался проектным решением, и перенос (пункт 7) оказался сделан
**раньше** пунктов 3–6, то есть до того, как алгоритм устоялся. По старому правилу каждое изменение
алгоритма пришлось бы сначала писать на Python, выгружать фикстуры, переносить в Rust и заново
прогонять гейты — тройная работа ради Python-пути, который в 9.6× медленнее и которым дальше никто
не пользуется.

С этого коммита:

- **изменения алгоритма делаются в Rust.** Пункты 3–6 дорожной карты и всё, что после них,
  проектируется, пишется и проверяется в `crates/`; ничего не прототипируется в `sherd_refit/`;
- **`sherd_refit/` заморожен на коммите `9cbcbbc`** и остаётся в репозитории как **эталон сверки
  для тех стадий, которые уже описаны в R** (`ALGO_REF` = `9d4b9d3`), и только для них. Пакет не
  удаляется и не «уходит на пенсию»: шестнадцать строк сверки — это доказательство того, что
  шестнадцать стадий порта делают то, что написано в R, и его стоит держать зелёным;
- **гарнитура сверки (`sherd-parity`, `tools/dump_fixtures.py`, `tools/compare_fixtures.py`,
  восемь дампов) заморожена вместе с ним**: `parity --stage all` в обоих режимах на восьми дампах
  остаётся гейтом (23 804 проверки, 0 отказов), но **новых строк в неё не добавляется** — у стадии,
  написанной после этого коммита, нет второй стороны для сравнения;
- **гейт качества для всей новой работы — `tools/evaluate.py` на наборах с эталонной разметкой при
  сидах 0–4**, его гоняет `tools/quality_gate.py` (см. ниже). Один прогон сравнивать с R §13 нельзя:
  там не числа, а **полосы**, измеренные разбросом по сидам. `parity` отвечает на вопрос
  «порт по-прежнему воспроизводит эталон?», `quality_gate.py` — на вопрос «алгоритм стал лучше?»,
  и после этого коммита к новой работе применим только второй.

Следствия: **фаза 3a (`pyo3`) снимается** — её критерий выхода («Python-конвейер с Rust-ядрами
воспроизводит Rust CLI») ведёт обратно к пакету, в котором алгоритма больше нет, — а имя
`sherd-refit` можно передать Rust-бинарнику, когда команда захочет: Python теперь тестовый эталон,
а не продукт.

### Что программа говорит музею: три полосы уверенности, картинки и файл ограничений

Пункт 3 дорожной карты. Всё, что ниже, — только в Rust-ядре (`sherd-refit-rs`), и всё выключается.

#### Три полосы уверенности (`--tiers on|off`, по умолчанию включено)

Раньше отчёт делил кандидатов надвое: пороги R §6.5 приняли — стык; не приняли — не стык.
Замер задачи M1 (2 916 кандидатов на восьми наборах при сидах 0–4) показал, что этого мало:
среди принятых стыков есть **ложные с верной геометрией** — черепок сдвинут вдоль шва на
0.7–1.1 толщины стенки, и все пять оценок R §6 у него такие же, как у настоящего.

Поэтому каждый принятый кандидат теперь проверяется ещё шестью пробами и попадает в одну из трёх
полос:

| полоса | что это значит | что с ней делает программа |
|---|---|---|
| **confirmed** — подтверждён | прошёл строгий набор порогов **и** устоял под пробами | **сборка строится только из них** |
| **probable** — вероятен | пороги R §6.5 прошёл, строгие — нет | в отчёт и в картинки — по убыванию оценки, первые `--probable-top` строк (по умолчанию 100); **не ставится** |
| **rejected** — отклонён | не прошёл R §6.5 | в отчёт, с причиной |

Пробы: насколько кандидат опережает **вторую** позу той же пары и **как далеко** эта вторая поза
стоит; сдвигается ли поза, если её подтолкнуть на полстенки вдоль шва; выживают ли оценки на двух
независимых перевыборках точек; двигается ли ответ ICP от возмущения входа в один ULP; сколько
**независимых** стыков коллекции согласны с тем, куда поставлен черепок; и приходит ли **тот же
самый поиск, запущенный заново на другой выборке точек**, в ту же позу. Пороги выбраны по таблицам
M1 и S3 и не подбирались заново; каждый — отдельный флаг (`--tier-min-tight`, `--tier-max-gap`,
`--tier-min-seam`, `--tier-min-cont-n`, `--tier-max-pen`, `--tier-max-slide`, `--tier-margin`,
`--tier-support`, `--tier-margin-rival`, `--tier-rival-moved`, `--tier-research`,
`--resample-seeds`).

**Правило подтверждения — дизъюнкция из двух плеч**, и второе из них задача S3 переписала по
таблице из 45 прогонов (`docs/superpowers/notes/2026-09-11-s3-recall.md`):

* **опора** — хотя бы один независимый стык коллекции ставит черепок туда же. Не изменилось;
* **отрыв** — кандидат опережает **лучшую** вторую позу пары не менее чем вдвое, эта вторая поза
  стоит не ближе **пяти толщин стенки** (иначе это тот же шов, сдвинутый вдоль себя, — а обогнать
  сдвиг не значит доказать смещение), и **независимый повторный поиск** той же пары на другой
  выборке приходит в ту же позу.

До S3 второе плечо читало вторую позу из тех пяти кандидатов, что возвращает R §5.7, ни о каком
расстоянии не спрашивало и повторного поиска не делало. Беда в том, что эти пять поз почти всегда
совпадают: у четырёх принятых кандидатов из пяти второй позы в списке просто не было, и плечо не
могло сработать вовсе. Теперь вторая поза ищется в **полном** списке R §5.6 — том, который `keep`
выбрасывал, — а если и там одна поза, доводится лучшая из отброшенных поз stage-1. Итог на наборах
разработки: **225 верных подтверждённых стыков вместо 169 и по-прежнему ни одного ложного**, полнота
17.4 % → **23.2 %**, и она выросла на каждом наборе. Цена — 8 стыков, которые старое правило
подтверждало по отрыву от случайно отличавшейся позы из пяти; они остались в полосе probable с
написанной причиной. `--tier-rule m1` возвращает правило M1 целиком, одним флагом.

В таблице `Confirmed joins` последний столбец `arm` говорит, **какое из двух плеч** подтвердило
именно этот стык.

Отдельное правило той же природы: если хотя бы у одного из двух фрагментов меш не замкнут, проверка
проникновения R §6.4 **не может быть выполнена** — и это отказ, а не пропуск. Такой стык остаётся
`probable` с причиной «penetration not measurable»: полоса confirmed — это утверждение о
доказательствах, а здесь одного из пяти доказательств просто нет (R §6.5 читает тот же ноль как
«проникновения не найдено» — это арифметика эталона, и она не менялась). На наборах разработки не
замкнуты три фрагмента `pot_B` (02, 07, 08) и один `pot_C` (01); на пяти наборах, где замкнуты все,
правило не двигает ничего.

Цена — полнота: на девяти наборах разработки при сидах 0–4 подтверждено **225 стыков и ни одного
ложного**, это 23.2 % соседних пар эталона (гейт качества печатает обе цифры последней строкой
каждого прогона — см. «Гейт качества»). Остальное — в разделе `Probable joins`, у каждой строки
написано, какая именно проба её не пропустила. Раздел `Candidates by fragment` — тот же список, но
по фрагментам: для каждого черепка его лучшие партнёры, лучшая полоса сверху. Это рабочий лист для
стола реставратора.

Полоса probable печатается **по убыванию оценки и не целиком**: по умолчанию — первые сто строк, а
над таблицей стоит, сколько показано из скольких («100 of 2761 shown»). `--probable-top N` меняет
это число, `--probable-top 0` печатает всю полосу. Тот же срез применяется к `Candidates by
fragment` и к `--review-images`, чтобы строка, картинка и счётчик не расходились; **`report.json`
не режется никогда** — в нём всегда все кандидаты, которые нашёл прогон. На маленьких наборах
(терракота, `pot_*`, `synthetic_20`) полоса короче ста строк, и флаг там ничего не меняет.

**«Ни одного ложного» — это про наборы разработки.** Финальная приёмка (10 сентября 2026) прогнала
полосы на трёх больших коллекциях: на двух синтетических — 148 подтверждённых стыков и снова ни
одного ложного, а на настоящей смешанной коллекции из десяти горшков — **10 ложных из 51**, три из
них между разными горшками. Что именно там происходит и что с этим делать за столом — ниже, в
разделе «Настоящая коллекция: чего ждать от прогона».

`--tiers off` возвращает поведение до пункта 3, файл в файл и байт в байт.

#### Картинки для проверки (`--review-images`)

С этим флагом на каждый подтверждённый и вероятный стык пишется `review/<A>__<B>.png` — три вида
пары, поставленной в найденную позу:

- **A серый, B оранжевый** — те же два первых цвета, что и в превью группы;
- **белым** — воксели шва (`t/3`), ровно те, число которых и есть оценка `seam`;
- **точки излома B покрашены по расстоянию до поверхности излома A**: зелёные ближе порога
  плотного прилегания, жёлтые — ближе предела зазора, красные — дальше. Красная кайма по контуру
  B — это его собственные края излома, которым здесь не нашлось пары; так и должно быть;
- три направления взгляда: вдоль средней нормали внешней поверхности **на шве** и вдоль внешних
  нормалей каждого из двух фрагментов;
- подпись сверху: оценки, полоса, отрыв от второй позы, сид.

Картинки детерминированы: два прогона одной коллекции дают одинаковые байты. В `report.md`
раздел `Candidates by fragment` ссылается на них столбцом `image`.

#### Файл ограничений (`--constraints constraints.json`)

Реставратор знает то, чего не знает геометрия. Файл — способ это сказать:

```json
{ "version": 1,
  "must_not_join":    [["FY234007_reduced", "FY234104_reduced"]],
  "must_join":        [["FY234021_reduced", "FY234094_reduced"]],
  "same_object":      [["FY234094_reduced", "FY234104_reduced"]],
  "different_object": [["FY234007_reduced", "FY234021_reduced"]] }
```

Это **рабочий файл целиком**: все четыре имени — сканы тестовой коллекции
`input/test_fragments_1/fragments`, и он проверен на ней (прогон завершается успешно, раздел
`## Constraints` печатает все четыре строки и то, что каждая сделала). Имена в файле — это имена
файлов без расширения, ровно как в столбце `fragment` отчёта; **имя из другой коллекции — ошибка, а
не пропуск**, поэтому файл пишется под ту коллекцию, на которой его запускают. Вместо пары в
`must_join` можно написать объект `{"a": …, "b": …, "pose": [[…]]}` с матрицей 4×4 — тогда
сопоставление для этой пары пропускается, а поза берётся из файла (строка `must_join` с позой в
таблице ниже).

| список | что делает |
|---|---|
| `must_not_join` | пара выбрасывается **до сопоставления** — она не считается вовсе; если кандидат по ней всё же дошёл до сборки, он отклоняется |
| `must_join` без позы | пара сопоставляется с увеличенным бюджетом второго прохода, её лучший **вероятный** кандидат повышается до подтверждённого и предлагается сборке **первым**. Если принятого кандидата нет — в отчёте `unsatisfiable`, и прогон всё равно завершается успешно |
| `must_join` с позой `4x4` | сопоставление для пары пропускается, поза становится подтверждённым кандидатом. Оценки R §6 всё равно считаются — **в этой позе** — и печатаются в отчёте рядом с тем, что позу задал человек |
| `same_object` | читается пунктом 4: пара считается одним объектом при подсчёте согласия, а если сборка развела эти два черепка по разным объектам — об этом сказано в `## Objects` |
| `different_object` | пара **сопоставляется и получает оценки как обычно** (в отличие от `must_not_join`), но **не ставится**: сборка отклоняет любой кандидат по ней с явной причиной, и она же не даёт слить две группы, в которых лежат эти два черепка, — по любому пути между ними |

Правила проверки строгие: неизвестное имя фрагмента — **ошибка**, а не пропуск; пара, названная
дважды одним именем, — ошибка; пара, попавшая в два списка, — ошибка; `pose`, которая не является
жёстким преобразованием, — ошибка; `version` иной, чем 1, — ошибка. **Ограничение никогда не меняет
оценку**: оно меняет только то, какие пары сопоставляются, из каких кандидатов сборке разрешено
строить и в каком порядке она их видит. Раздел `## Constraints` в `report.md` перечисляет каждую
строку файла и то, что она сделала.

#### Настоящая коллекция: чего ждать от прогона

Всё выше показано на маленьких наборах. Вот что получается на коллекции музейного размера. Числа —
замеры финальной приёмки 10 сентября 2026 (`docs/superpowers/notes/2026-09-10-a1-acceptance.md`) на
MacBook с M2 Pro (10 ядер, 16 ГБ), CPU, `--no-preview --no-meshes --memory-budget 4.83`. Набор
`input/sfspp/mixed_all` — это **164 настоящих черепка десяти разных горшков**, самая честная
имитация музейного ящика, какая у нас есть.

| | один горшок, 164 куска (`synthetic_170`) | **десять горшков, 164 черепка** (`mixed_all`) |
|---|---|---|
| время прогона | **18.5 мин** | **30.3 мин** |
| пик памяти | 2.6 ГиБ | 1.8 ГиБ |
| **confirmed** — программа ставит | **48–51** стык, **все верные** | **23–28** стыков, из них **4–6 ложных** |
| **probable** — смотреть глазами | **92–94** строки, верных 81–88 | **2 761–2 795** строк, верных **61–62** |
| собрано групп (больше одного куска) | 20–21, самая большая 9 | 16–17, самая большая 5 |

Читать это надо так.

1. **На одном сосуде полосе confirmed можно верить.** Четыре прогона двух синтетических коллекций
   дали 148 подтверждённых стыков, и все 148 — верные; межобъектных стыков ноль даже там, где в
   коллекцию нарочно подложены шесть кусков чужого сосуда.
2. **На смешанной коллекции — нельзя.** Из 51 подтверждённого стыка `mixed_all` на двух сидах
   **десять ложных**, и три из них склеивают горшок E с горшком I. Причина измерена и записана: у
   этих двух горшков **одинаковая толщина стенки и одинаковый радиус кривизны** — в одной из групп
   черепки сходятся с точностью до 0.046 мм, — а разделение объектов (пункт 4) имеет право
   отклонить стык только по признаку, который разделяет объекты лучше AUC 0.800; лучший измеренный
   даёт 0.740. Пока не появится признак, который различает эти два горшка (цвет черепка, состав
   глины, толщина в другом месте), **на смешанной коллекции полосу confirmed надо проверять
   глазами так же, как probable**.
3. **Список probable на смешанной коллекции длинный, но отсортированный.** 2 761 строка (сид 0;
   2 795 на сиде 1), верных в ней 61 — то есть 2 %. Но строки идут по убыванию оценки, и **первая
   сотня содержит четыре пятых всех верных стыков списка**, причём каждая вторая из этой сотни —
   настоящая. Остальные 2 661 строка стоят ещё двенадцати стыков на сиде 0 и одиннадцати на сиде 1.
   Практический вывод: работать сверху вниз и остановиться примерно на двухсотой строке; это
   рабочий день, а не рабочий месяц. Поэтому `report.md` по умолчанию и печатает **первую сотню**:
   `--probable-top N` меняет длину (`--probable-top 0` — весь список), а над таблицей написано,
   сколько строк показано из скольких («100 of 2761 shown»). В `report.json` полоса всегда целиком,
   сколько бы ни показал `report.md`.
4. **`--review-images` пишет картинки на тот же показанный список.** Одна картинка на каждый
   подтверждённый стык и на каждую строку показанной части полосы probable — то есть на настройках
   по умолчанию это 23 + 100 картинок, около **80 МБ и трёх секунд** при измеренных (задача T2)
   26 мс и ~0.64 МБ на картинку. С `--probable-top 0` картинок будет 2 784: примерно **минута
   работы и около 1.8 ГБ PNG**; считайте место заранее.
5. **`--constraints` — главный инструмент на смешанной коллекции, но читайте, что именно делает
   каждый список.** `different_object` убирает именно тот класс ошибок, который геометрия здесь
   сделать не может (склейку двух горшков), — однако он работает **в сборке, а не до
   сопоставления**: пара всё равно сопоставляется, получает оценки и полосу, и только поставить её
   сборке запрещено; в `report.md` она остаётся в `## Confirmed joins`, а `## Confirmed joins not
   used` называет её с причиной. **Прогон от этого не становится быстрее ни на секунду.** Взамен вы
   видите, что геометрия думает о вашем утверждении, — и запрет держится не только на этой паре: он
   не даёт слить две группы ни по какому пути между ними. Второе: список принимает **пары
   фрагментов**, а не имена горшков; развести Pot_E и Pot_I на `mixed_all` — это 34 × 30 = **1 020
   строк**, поэтому на практике им закрывают несколько конкретных подозрительных пар, а не два
   горшка целиком. Если пару надо выкинуть из прогона совсем — это `must_not_join`: **вот он и
   правда снимает пару до сопоставления** (и экономит её время). `must_join` заставляет проверить
   ту пару, на которой настаивает реставратор.
6. **Один сид — это одна попытка.** На `mixed_all` — то есть на коллекции, о которой этот раздел, —
   между сидом 0 и сидом 1 совпадает **12 стыков из 23 и из 28** (52 % и 43 %), а **20 из 27**
   (74 %) разошедшихся — это стыки, которые на другом сиде всего лишь `probable`; ещё 7 на другом
   сиде не были найдены вовсе. На двух синтетических коллекциях совпадение выше (15 из 26 и 33 из
   51), поэтому среднее по трём коллекциям — «около трёх пятых» — для смешанной слишком
   оптимистично. Стык, подтверждённый на **двух** прогонах с разными `--seed`, — заметно более
   сильное утверждение, чем стык, подтверждённый на одном, и это измерено: из десяти ложных
   подтверждённых стыков `mixed_all` **ни один не подтверждён на обоих сидах**, а из 41 верного
   на обоих подтверждены 29 (`docs/superpowers/notes/2026-09-10-c-closure.md` §4). Автоматически
   программа этого пока не делает: два прогона надо запустить руками и сравнить списки.

Не забывайте про правило замкнутости: у `mixed_all` **5 черепков из 164 не замкнуты**, и
**16 из 288 настоящих смежных пар (5.6 %)** касаются одного из них — такие стыки никогда не попадут
в confirmed, потому что проверку проникновения на них выполнить нельзя.

### Что программа говорит об объектах: согласие внутри группы (`--objects on|off`)

Пункт 4 дорожной карты. В смешанной коллекции — несколько разбитых сосудов сразу — самая дорогая
ошибка не «не собрал», а «склеил два горшка». Базовая мера на `mixed_ABG` (24 фрагмента, три
горшка): 3 межобъектных стыка при чистоте групп 0.864.

#### Что считается и что печатается

При предобработке каждый фрагмент получает свою **таблицу признаков** — толщина стенки, радиус
сферы по внешней поверхности, шероховатость излома, диаметр по оси вращения, цвет черепка в CIE
Lab, если файл несёт цвета вершин, — и она кладётся в кеш (`cache_version` 6; кеш прошлой версии
пересчитывается сам). Каждая собранная группа печатается в `report.md` разделом `## Objects` как
**объект**: медиана и MAD его участников по каждому признаку, диаметр венчика, если хоть один
фрагмент помечен как венчик, и те участники, которые в это согласие не укладываются.

#### Ни один признак ничего не запрещает — и это замер, а не осторожность

Правило аудита: признак получает право **вето** только там, где его измеренная разделяющая
способность (AUC) выше 0.800. Задача M1 измерила все девять признаков на всех коллекциях, где
принадлежность предмету известна по-настоящему (`mixed_ABG`, `mixed_all`, объединённые pot_A–H), и
лучший результат — **0.740**. Поэтому список `--object-demote` пуст: числа печатаются, решение
принимает реставратор. Единственные значения выше 0.8 нашлись на синтетическом наборе, где «другой
объект» — шесть кусков специально сделанного второго сосуда, то есть свойство генератора, а не
керамики.

Цвет измерить не на чем: сканы SfS++ несут по одному цвету на файл, синтетика — почти постоянный
терракотовый, а единственные настоящие цвета в тесте — четыре музейных скана, и они один объект.
Признак посчитан и проверен, ждать ему нужно материал музея.

#### Что действительно происходит

| поведение | что делает | флаг |
|---|---|---|
| **согласие группы** | печатает медиану и MAD по объекту и называет участников вне согласия | `--object-demote` (пуст), `--object-k-mad` (3), `--object-min-members` (3) |
| **слияние групп** | **подтверждённый** стык между двумя группами объединяет их: проверка проникновения каждого фрагмента одной группы против каждого фрагмента другой и согласие со всеми стыками между группами. Раньше R §8 просто отказывал такому стыку | `--object-merge on\|off` (вкл.) |
| **взаимное противоречие** | два подтверждённых стыка в одной группе, расходящиеся в том, куда ставить фрагмент, понижаются оба | `--object-disagreement on\|off` (**выкл.**) |

Последнее выключено по замеру, а не по вкусу: в подтверждённой полосе на восьми наборах при сидах
0–4 **ноль ложных стыков**, ловить противоречию нечего, а включение снимает на `mixed_ABG`
**27 подтверждённых стыков из 38** по пяти сидам (8 / 7 / 7 / 7 / 9 становится 2 / 3 / 2 / 4 / 0) —
все верные, и все такие, которые сборка R §8 уже развела сама.

`same_object` и `different_object` из файла ограничений читаются здесь: `different_object` не даёт
слить две группы (и по-прежнему не даёт поставить стык), `same_object` снимает понижение по
согласию для этой пары и печатается, если сборка всё же оставила эти два черепка в разных объектах.

`--objects off` возвращает поведение до пункта 4, файл в файл и байт в байт.

### Гейт качества: `tools/quality_gate.py`

```bash
python tools/quality_gate.py                    # восемь наборов, сиды 0-4, CPU
python tools/quality_gate.py --sets pot_C pot_H --seeds 0 1   # подмножество
python tools/quality_gate.py --out output/quality/scored \
    --score-only mixed_all output/acceptance/mixed_all/seed0   # посчитать готовый прогон
```

Гоняет `sherd-refit-rs run --backend cpu --no-preview --no-meshes --seed s` при `s = 0…4` на всех
восьми наборах разработки (терракота, `pot_A/B/C/G/H`, `synthetic_20`, `mixed_ABG`), считает каждый
прогон через `tools/evaluate.py` и пишет **одну таблицу** — точность по фрагментам, precision,
четыре корзины стыков (`correct` / `wrong pose` / `non-adjacent` / `cross-object`), чистоту групп и
время — в `output/quality/quality.md` и `output/quality/quality.json`.

Под таблицей у каждого набора **два вердикта**, и это разные вещи.

- **Гейт** — то, что в R §13 записано как **запрет**: последняя строка (межобъектных стыков 0,
  чистота групп 1.000) на семи однообъектных наборах, правило `pot_G` («не больше двух стыков, и
  каждый — стык с неверной позой на паре, смежной по эталону») с его нулевой точностью, и строка
  решений терракоты. Нарушение любого из них — ненулевой код выхода. На этом дереве все три запрета
  держатся на всех пяти сидах — **но сам прогон гейта завершается кодом 1**: не проходит строка
  *полноты* терракоты (девять из десяти слотов «сид × стык», см. ниже). Красный прогон здесь — это
  не нарушенный запрет, и последняя строка вывода говорит, что именно из двух случилось.
- **Полоса** — приведённый в R §13 **разброс** точности по фрагментам и precision; он показывается,
  но не гейтится. Эти полосы — пять собственных выборок **эталона** (задачи Y и Z), а пять выборок
  порта — вторая выборка той же хаотичной величины, а не подмножество первой. Задача H4 измерила,
  что у порта разброс шире на трёх наборах из семи: `pot_A` 0.750 на сиде 2 против 0.875–1.000,
  `pot_B` 0.778 / 0.857 на сидах 2 и 4 против 0.889–1.000 / 1.000, `pot_H` 0.000 на сиде 2 против
  0.273–0.364. Гейтить одну выборку из пяти другой такой же — значит валить прогон за **жребий**, а
  не за **изменение**; строка полосы нужна ровно для того, чтобы шаг, который вывел набор из
  разброса эталона или вернул его туда, был обязан это сказать. Убирать этот разброс — задача
  шагов 8 и 10 плана D §12.

`mixed_ABG` при `--tiers off` сравнивается с базовой строкой D §10.3, а не с гейтом. При `--tiers
on` (по умолчанию) на нём стоят обе строки аудита §E, пункт 10: **запрет** — межобъектных стыков 0 и
чистота групп 1.000 **в полосе confirmed** на каждом сиде, и **пол по полноте** — не меньше 12
верных стыков в полосах confirmed и probable **вместе**. Двенадцать — это число стыков, которые
сборка R §6.5 использовала до появления полос; полосы не добавляют ни одного стыка, который R §6.5
отверг, поэтому сравнивать с этим числом можно только две верхние полосы вместе — и это же тот
список, с которым работает реставратор. Число верных **confirmed**-стыков печатается по сидам и
намеренно не гейтится: порог, подогнанный под то, что полоса даёт сегодня, завалит любой будущий
шаг, который разменял подтверждённый стык на более осторожное правило.

Строка терракоты («оба стыка R §13 — confirmed на каждом сиде») — это **десять** ячеек
(сид, стык), и гейт требует десяти. На этом дереве их девять: на сиде 4 у пары 021–094 поиск
возвращает единственную позу, обгонять нечего, а цепочка из трёх фрагментов не даёт второго пути
для опоры. Гейт на этом падает и говорит, что это строка **полноты**, а не запрет: ничего сверх
двух стыков R §13 не подтверждается ни на одном сиде, и оба стыка на каждом сиде как минимум
probable. Подробности и две проверенные (и отвергнутые) попытки закрыть ячейку —
`docs/superpowers/notes/2026-09-10-g-tiers-findings.md`.

У терракоты нет выложенной эталонной разметки (ручная сборка музея никогда не записывалась позами),
поэтому её строка в R §13 — это набор **решений**, и скрипт проверяет их прямо по `report.json`: ровно
два стыка 021–094 и 094–104 и никаких других, 007 не поставлен, оба проникновения 0, обе плотности
контакта ≥ 0.27, оба шва в пределах 20 % от 20.3 t и 10.7 t. В таблице её колонки от `evaluate.py`
стоят прочерками — это отсутствующая разметка, а не отсутствующее измерение.

Почему это Python, а не подкоманда бинарника: метрика — это `tools/evaluate.py` и ничего больше.
Двойник на Rust пришлось бы писать заново — корзины, ошибку позы по центроиду, взвешивание чистоты, —
и два счётчика, которые могут разойтись, хуже одного на языке, который для метрики уже нужен
(numpy и Open3D). Скрипт импортирует `evaluate` как модуль, а не вызывает процессом: Open3D
поднимается один раз на сорок прогонов, а центроиды каждого набора читаются один раз вместо пяти.
Рабочая папка набора переиспользуется между сидами, поэтому кеш фрагментов строится только на первом:
другой сид пересчитывает три выборочных массива R §3.5 и больше ничего (R §3.7).

Замерено на настройках по умолчанию: **сорок прогонов за 10.0–10.3 мин** на M2 Pro (10 ядер) при
бюджете в 25 минут — пять прогонов одних и тех же сорока (задачи O1, G, A1, V8, V9) дали 602.2,
610.9, 611.7, 614.9 и 602.6 с; каждый пишет своё время в `meta.wall_total_s` своего
`quality.json`. Около двух пятых этого — полосы уверенности: те же сорок прогонов с `--tiers off`
занимают 412.2 и 459.8 с. `--render-only` пересобирает таблицу из JSON готового прогона, не
запуская ничего заново.

`--score-only ИМЯ ПАПКА` считает **уже сделанный** прогон и пишет для него ту же таблицу. Так
оцениваются три приёмочных коллекции — `synthetic_60`, `synthetic_170` и `mixed_all`: правило
малых наборов (D §12) запускает их ровно один раз, на финальной приёмке, поэтому их нет в списке
наборов скрипта и обычный прогон до них не доберётся. Сид, время и ключи `--tiers`/`--objects`
такая строка берёт из `report.json` самого прогона, а не из флагов скрипта: прогон делал не он.
Запрет на этих коллекциях — тот, что записан в шаге 12: межобъектных стыков 0 и чистота групп
1.000 **в полосе confirmed**.

  В injected-режиме совпадение с Python **точное** на всех 68 фрагментах восьми коллекций

- брейклайны и их рамки (R §3.5.3–3.5.5): точки — середины рёбер между черепком и сколом,

- сэмплированные match-массивы (R §3.5.1–3.5.2, §3.5.6): 20 000 точек по всей поверхности с

  розыгрыш (PMC-9), поэтому сами точки не совпадают с numpy: в injected-режиме сходятся все

- `sherd-refit-rs segment DIR --out OUT` — препроцессинг всей коллекции через кеш; два запуска

- сопоставление пары до отбора кандидатов (R §1.2, §4.2, §5.1–5.3): масштабы пары
  `max(k·t, m·res)` при `t = min(t_A, t_B)` и `res = max(res_A, res_B)`, гипотезы из пар рамок
  брейклайна с фильтром по двугранным углам (`|dih_A + dih_B − 180| < 25°`) и отображением

Семафор по памяти из D §5 сделан (шаг E2): флаг `--memory-budget GB` держит препроцессинг в
заданном объёме памяти — на терракоте при `--memory-budget 0.5` сканы обрабатываются по одному и
пишут те же кеши бит в бит, что и без ограничения, при 835 МиБ пика вместо 1 451. Общий кеш
`MatchData` оттуда же был сделан там же и **снят в H2**: измерено 0.9 % CPU и ноль по стенным
часам (аудит §B.8), выходные файлы от снятия не сдвинулись ни на байт.

Задача H3 закрыла два оставшихся места, где память никто не считал (аудит §B.2, §B.3). Доводка
R §9 читает исходный скан каждого собранного фрагмента и делала это без всякой брони — теперь она
берёт то же разрешение семафора, что препроцессинг и писатели R §11.4, и под `Budget::bytes(1)`
читает по одному скану и выдаёт те же облака бит в бит. Оба BVH (по трещине — R §6.1, по всему
мешу — R §6.4) жили до конца процесса, хотя последний их читатель заканчивается вместе с
сопоставлением: измерено на `synthetic_20` — **472 МБ** и **46 МБ**, то есть 129 и 12.5 байта на
грань рабочего меша, около 4.4 и 0.4 ГБ на 170 фрагментах D §8. Теперь они освобождаются сразу после
второго прохода, до доводки и вывода — двух этапов, которые держат по полному скану на задачу;
на месте освобождения возвращается 217–276 МиБ. Не LRU: при переборе всех пар живы деревья всех
фрагментов сразу, поэтому кеш меньше коллекции только молотит впустую, а размером с коллекцию —
это и есть то, что было. Пиковая резидентная память теперь печатается по этапам в каждом запуске
и лежит в `report.json` рядом с `timings`.

Фаза 2a (шаг G1) сделана: граница `Executor` из D §6.1 стала настоящей — грубая оценка, ступень
ICP, ограниченное расстояние до поверхности и тест «внутри» ходят через батч-структуры, а CPU при
этом **не сдвинулся**: 92 выходных файла четырёх наборов совпадают с `9bf35d6` бит в бит, таблица
сверки — 23 804 проверки, 0 ошибок. Появился крейт `sherd-gpu`: перечисление адаптеров и
`--gpu-adapter NAME|INDEX`, проверка лимитов по умолчаниям wgpu, нарезка батчей под 128 МБ и
двумерная сетка за пределом в 65 535 групп, LRU из 32 слотов фрагментов на 400 МБ (снят в H2:
резидентный набор D §6.3 так и не получил вызывающего — ядро грузит цель *пары* на радиусе
*ступени*, а не фрагмент) и самопроверка D §6.8 на двух ядрах, которые измерил эксперимент E7: свёртка 1e7 чисел `f32` в фиксированном
порядке **бит в бит** совпадает с CPU (`0x49a7230c`), а ядро поиска ближайшего соседа по решётке
D §6.2 расходится с CPU на 1 запросе из 384 000 — и это ничья с разницей 1.0e-8 при худшем
расхождении расстояния 1.3e-7. Измеренная скорость — **12.2–17.9 нс на запрос, 3.3–6.3× против
всех десяти ядер CPU**; это подтверждает оценку E7 и опровергает исходное допущение D §6.6.
`--backend gpu` открывает устройство, гоняет самопроверку и **падает с внятной ошибкой**, если
адаптера нет или проверка не прошла; `--backend auto` в фазе 2a всё равно выбирает CPU и пишет
почему — у исполнителя ещё нет ядер. Подробности:
`docs/superpowers/notes/2026-09-08-g1-gpu-foundation.md`.

Фаза 2b (шаг G2) сделана: на устройстве работают **два ядра матчинга** — грубая оценка R §5.2
(`kernels/coarse.wgsl`, одна рабочая группа на гипотезу, наружу выходит целочисленный счётчик, а
деление на 60 делает хост в `f64`, как в CPU) и ступень ICP R §7 (`kernels/icp.wgsl`, 256 полос на
кандидата, **все итерации внутри одного диспатча**, 29 аккумуляторов сворачиваются деревом в
фиксированном порядке, а нулевая полоса решает 6×6 через LDLT с правилом выбора ведущего элемента
Eigen или 3×3 Умеямы через односторонний Якоби). Обе тучи сдвигаются в свои центроиды в `f64` — это
предписание D §7 для `f32`-пути, — и для точка-плоскость к обновлению добавляется поправка
`(R − I − ω̂)·c`, без которой сдвиг превращается в `Assembly::Centred` из D §7 (0.044 t по медиане).
6×6 перед разложением **эквилибрируется**: p90 расхождения позы падает с 6.5e-2° до 7.1e-4°.

Измерено: грубая оценка совпадает с CPU **бит в бит на 2 934 052 гипотезах из 2 934 122**, а 70
расхождений — ровно по одной пробной точке из шестидесяти (эффект FMA, E7 §5.1). Ступень 1
укладывается в строку D §10.2 (0.05°) на семи наборах из восьми, ступень 2 — на четырёх из восьми,
и «хвост» на остальных отделён контрольным прогоном: там, где та же лестница в `f64`, запущенная от
позы, с которой реально стартует устройство, уходит на 1.96° (pot_C), виновата не арифметика ядра.
Сквозной прогон на семи наборах: **используемые стыки, группы и все оценки `tools/evaluate.py`
совпадают с CPU полностью**, два прогона на GPU совпадают побайтно.

Скорость честная и неутешительная: стадия матчинга — **1.21× на одном потоке и 1.0× на десяти**.
Устройство занято 6.35 с из 15.4-секундной стадии на `synthetic_20`, остальное время оно простаивает,
пока десять потоков rayon по очереди блокируются на нём; ядра сами по себе дают 1.6–4.2×. Нужен
блочный планировщик D §6.4 («потоки CPU готовят, один поток отправляет, двойная буферизация»), и он
не сделан — поэтому `--backend auto` по-прежнему выбирает CPU и печатает эту цифру. Подробности:
`docs/superpowers/notes/2026-09-08-g2-kernels.md`.

Фаза 2d (шаг G3) сделана: программный конвейер D §6.4 построен, и заодно выяснилось, что очередь
перед устройством была **не устройства, а хоста**. `wgpu::Device::poll` — не ожидание одного
потока: каждый рабочий поток, отдавший батч, входит в замки самого устройства, и девять потоков
стоят там по очереди. Три измерения на `synthetic_20`: стадия переставала ускоряться уже на
**четырёх** потоках (16.08 с против 15.97 с на девяти); при восемнадцати потоках профиль показывал
**4.9 занятых ядра из десяти**; те же 330 отправок, которые на одном потоке проходят за **6.4 с**,
на девяти растягивались на 14 с настенного времени.

Сделано: `sherd_gpu::pipeline::Submitter` — **один поток отправки**, владеющий всеми `submit`,
`poll` и `map_async`, с четырьмя командными буферами в полёте (замерено: 4 лучше 2 и лучше 8);
`Executor::device_slack` — пул матчинга в полтора раза глубже (1.93× при `--threads 1`, 1.36× при
четырёх, 1.00× при девяти); одна отправка на вызов `Executor` вместо одной на диспатч плюс одной на
чтение (658 отправок → 330); `Occupancy` — честная занятость устройства как объединение интервалов,
а не сумма по потокам (та показывала 85.6 с для 13.4-секундной стадии). Плюс `--gpu-memory GB` и
резервирование по D §1 (пик на `synthetic_20` — **103 МБ** из 1 ГБ), отмена и прогресс из D §5 с
Ctrl-C, и тесты на нарезку диспатчей под TDR и двумерную сетку.

Итог: стадия матчинга — **1.04–1.40×** на семи наборах (было 1.0×), занятость устройства выросла с
41 % до 68 %. Двух крат не будет, и причина не в планировщике: **устройство и десять ядер делят
один бюджет питания и полосы памяти.** Те же 330 отправок той же работы занимают 5.66 с времени
устройства при одном рабочем потоке и 9.06 с при девяти — устройство теряет **1.60×** собственной
пропускной способности по мере загрузки CPU, и минимум стадии приходится на **шесть** потоков
(11.86 с), а не на девять (13.38 с). Поэтому `--backend auto` по-прежнему выбирает CPU: планка
D §6.8 — 1.5×. Ядра BVH (фаза 2c) **осознанно не сделаны**: R §6 — это 15.9 % процессорного времени
GPU-прогона, но перенос отнимет от стадии не больше 1.2 с и добавит 43.7 млн запросов к устройству,
у которого запаса 4.3 с. Подробности: `docs/superpowers/notes/2026-09-08-g3-pipeline.md`.

Фаза 2e (шаг G4) сделана: два порога, каждый по измерению, и честный `info`.

**Что настроено.** Во-первых, у размера батча грубой оценки появился **потолок**
(`coarse::MAX_QUERIES` = 12 млн запросов) рядом с уже существовавшим полом: батч крупнее считает
CPU, потому что на встроенном GPU очень большой батч и ждётся долго, и тормозит те же десять ядер,
рядом с которыми он идёт. Во-вторых, **глубина пула сопоставления перестала расти без предела**:
`device_slack` теперь `min(⌈threads/2⌉, cores + 1 − threads)` — «по потоку на ядро плюс один,
который ждёт устройство», — так что на этой машине пул стал 11 рабочих потоков вместо 14. Оба
измерены по восьми-двенадцати чередующимся раундам (`cpu, base, вариант, …`) и по медиане парных
отношений внутри раунда, потому что абсолютное время на ноутбуке за сессию уплывает на четверть.

у частного медиан.)

Было 1.04–1.40× (G3), стало **1.07–1.43×**, и главное — набор, где устройству есть что считать,
`synthetic_20`, вырос с 1.08× до 1.28×. Ни одна склейка, ни одна группа и ни одна поза при этом не
сдвинулись: все три файла результата (`report.json` без секции времени, `report.md`,
`transforms.json`) на семи наборах **и на CPU, и на GPU** совпадают с тем, что писал G3, хотя на
`synthetic_20` потолок увёл с устройства 41 вызов грубой оценки из 190.

**Чего в этой выгоде нет.** G3 намерил, что `--gpu-memory 0.05` даёт 1.37×, и прочитал это как
«отказ семнадцати самым крупным батчам». Замер каждого резервирования показал другое: самый крупный
одиночный батч — **20.7 МБ** при пике в 100 МБ, то есть флаг отказывал не крупным батчам, а тем,
которые пришли, **пока устройство было занято**. Это свойство расписания, а не батча; ядро грубой
оценки совпадает с CPU не полностью (70 гипотез из 2.93 млн — на одну пробную точку), поэтому такое
правило разъехалось бы между двумя прогонами одной коллекции и сломало бы гейт побитовой
воспроизводимости D §7. Потолок по размеру батча — функция самого батча, и он этим свойством не
обладает.

`--backend auto` по-прежнему выбирает CPU: планка D §6.8 — 1.5× на стадии, измерено 1.07–1.43×.
Подробности: `docs/superpowers/notes/2026-09-08-g4-tuning.md`.

### GPU-бэкенд: как включить и чего ждать

**`--backend gpu` — это опция для тех, кто меряет ядра, и задел под дискретный адаптер, а не
рабочий режим.** Решение задачи H2 (аудит §A.2.4): `auto` остаётся на CPU **до тех пор, пока
стадия сопоставления не измерена на дискретном адаптере** — это политика
(`GpuExecutor::AUTO = AutoPolicy::CpuUntilADiscreteAdapter`), а не порог, который сдвинется от
следующей настройки. Причина измерена: на встроенном GPU устройство и десять ядер делят один
бюджет питания и полосу памяти, устройство теряет 1.6× своей пропускной способности, когда ядра
заняты, и стадия даёт 1.07–1.43× при планке D §6.8 в 1.5×. Дискретная карта ничего этого не делит,
поэтому её строки придётся мерить заново, а не наследовать; матрица вендоров и ядра BVH из D §12
вычеркнуты как несделанные (мерить их тут не на чем: один адаптер Metal, программного в macOS
нет). Дальнейшей настройки этого пути не будет; CPU-путь проходит все гейты D §10.3 с запасом
4–7×.

Флаги `run` и `bench`: `--backend auto|cpu|gpu` (по умолчанию `auto`), `--gpu-adapter NAME|INDEX`,
`--gpu-memory GB`.

- **`cpu`** — устройство не открывается вовсе.
- **`gpu`** — открывается адаптер, гоняется самопроверка D §6.8; если адаптера нет или проверка не
  прошла, запуск **падает** с внятной ошибкой, а не считает молча на CPU. Так время нельзя
  приписать не тому бэкенду.
- **`auto`** — то же самое, но решение по правилу D §6.8, и оно печатается словами. На этой машине
  выбирается CPU, и по политике выше, а не по одному числу.
- **`--gpu-adapter`** — индекс из `info` или подстрока имени; на этой машине адаптер один
  (Metal, Apple M2 Pro), программного адаптера в macOS нет, поэтому упавшую самопроверку не с чем
  сравнить (E7 §6).
- **`--gpu-memory GB`** — сколько ядра могут держать на устройстве одновременно (D §1, по умолчанию
  1 ГБ, `0` снимает ограничение). Батч, который не влезает, считает CPU, и `run` печатает, сколько
  таких было. Пик на `synthetic_20` — 100 МБ, отказов при значении по умолчанию нет.

**Самопроверка** — четыре проверки, и `sherd-refit-rs info` печатает их целиком: лимиты устройства;
свёртка 1e7 чисел `f32` в фиксированном порядке, которая обязана совпасть с CPU **бит в бит**
(`0x49a7230c`); ядро поиска ближайшего соседа по решётке против CPU (1 расхождение из 384 000, и то
ничья); и пропускная способность — 13.8 нс на запрос, **5.0× против всех десяти ядер**. `info`
печатает рядом и второе число — **1.07–1.43× на стадии сопоставления** — и объясняет разницу: ядро
меряется на свободном устройстве, а стадия идёт рядом с десятью занятыми ядрами, с которыми
устройство делит питание и полосу памяти.

**Что реально считает устройство:** грубая оценка R §5.2 и ступень ICP R §7, когда батч попадает
между измеренными порогами (`coarse::MIN_QUERIES` = 200 тыс. .. `MAX_QUERIES` = 12 млн запросов;
`icp::MIN_CANDIDATES` = 16 и `MIN_WORK` = 100 тыс.). Ограниченное расстояние R §6.1 и тест «внутри»
R §6.4 остаются на CPU (фаза 2c: измерено и отложено, G3 §6). **Любой** батч, который устройство не
берёт — мал, велик, не влезает в бюджет, или устройство ответило ошибкой, — считает эталонная
реализация на CPU; ответ от этого не меняется, а счётчики в конце прогона говорят, сколько таких
было по каждому из четырёх методов.

**Что реально считает устройство в прогоне** (не в `gpu-check --force-device`): грубую оценку
R §5.2 и две ступени этапа 1 по линии излома R §5.4. Этап 2 R §5.6 — всегда CPU, по политике
`icp::STAGE2_ON_DEVICE`: десять кандидатов при пороге в шестнадцать. На этой политике и
сформулирован критерий выхода фазы 2b (D §12): `gpu-check` выходит с нулём на семи наборах из
восьми, восьмой — pot_C, у которого одна ступень этапа 1 из тысячи кандидатов расходится на
9.1e-2° при допуске 0.05° (остановка ступени, а не точность — см. D §6.7). На уровне прогона
критерий выполняется на всех восьми: те же принятые стыки, те же группы, те же оценки
`evaluate.py`, а итоговые позы — внутри строки `refine` D §10.2.

Ещё нет: ядра BVH (фаза 2c, измерено и отложено, вычеркнуто из D §12), мультипарный батч D §6.5 и
Python-биндинги (фаза 3).
