# E2 — mesh IO: which crate reads and writes each format

**Date:** 2026-09-06. Branch `rust-core`. Plan row E2, design `2026-09-06-rust-core-design.md` §3
(rows "mesh read" / "mesh write"), algorithm reference `2026-09-06-algorithm-reference.md` §11.4.
**Machine:** Apple M2 Pro (10 cores, 16 GB), macOS 24.6.0, cargo 1.88, release build (`opt-level = 3`).
Other agents were running throughout, load average 4–9; every time below is the best of 5–21 runs
and is therefore an upper bound on a quiet machine.
**Reference:** Open3D 0.19.0 `o3d.io.read_triangle_mesh` / `write_triangle_mesh`, numpy 2.5.2,
Python 3.12.9.
**Candidates:** `ply-rs` 0.1.3, `ply-rs-bw` 4.0.1, `serde-ply` 0.2.2, `mesh-loader` 0.1.13,
`tobj` 4.0.5, `stl_io` 0.11.0, `gltf` 1.4.1, plus an own PLY reader/writer and an own OFF reader
as speed baselines.

**Recommendation**

| format | take | why |
|---|---|---|
| PLY read + write | **`ply-rs-bw` 4.0.1** | byte-exact against Open3D on all 11 PLY variants; its writer reproduces Open3D's file byte for byte; maintained (fuzz + Miri + API-compat CI, `forbid(unsafe_code)`); 1.5× faster than Open3D on binary files, 1.2× slower on ASCII |
| OBJ | **`tobj` 4.0.5** | keeps the file's own vertex list, reads `v x y z r g b` colours, about 2× faster than Open3D |
| STL | **`stl_io` 0.11.0** | binary and ASCII, `read_stl` lands exactly on Open3D's cleaned mesh |
| OFF | **own reader** (≈ 40 lines) | no crate on crates.io reads OFF; the own one matches Open3D exactly |
| GLB | **`gltf` 1.4.1**, `default-features = false, features = ["utils"]` | only candidate; reads COLOR_0 exactly. Two mandatory workarounds, §6 |
| — | **drop the own PLY parser** from D §3 | the crate passes every criterion; the own baseline's only advantage is speed nobody needs, and it panicked where the crates returned an error (§7) |
| — | **drop `mesh-loader`** | it has no PLY support at all (§2), and `tobj`/`stl_io` cover what is left |

The consequences for the design are collected in §8. Two of them are corrections: Open3D writes
`double` coordinates, not `float`; and its OBJ/STL/OFF/GLB readers return a vertex list that is
neither the file's nor one per face corner, so parity for those formats has to be measured after
`load_mesh`'s cleaning, never on the raw counts.

## 1. Method

`py/dump.py` reads every benchmark file with Open3D and writes a canonical dump (f64 `V`, u32 `F`,
u8 RGB — Open3D's `[0,1]` colours multiplied by 255 and rounded). A Rust harness runs one candidate
reader per invocation and writes the same layout. `py/compare.py` then reports, per pair of dumps:
exact array equality in file order, equality after a canonical reordering (vertices lexicographically
sorted, faces remapped and rotated so the smallest index comes first, then sorted), the maximum
absolute and relative coordinate difference, and the number of vertices whose colour differs.

Every comparison is made twice:

- **raw** — against `read_triangle_mesh(path)` exactly as it comes off disk;
- **clean** — both meshes pushed through `load_mesh`'s cleaning (`remove_duplicated_vertices`,
  `remove_degenerate_triangles`, `remove_unreferenced_vertices`) first. This is the operationally
  meaningful one: `fragment.load_mesh` cleans before anything else sees the mesh, and D §10.2's
  load-stage gate is "counts after cleaning — exact".

Benchmark files (21): the 4 terracotta scans (binary LE, `float` xyz + `uchar` RGB,
`list uchar int`, 14.5–27.5 MB, 0.7–1.34 M faces); 2 synthetic Pingsdorf fragments (binary LE,
`double` xyz **and** `double` normals + `uchar` RGB, `list uchar uint`); the same terracotta scan
re-written by Open3D as 29 MB ASCII and as an 18.8 MB binary; a hand-made **binary big-endian** PLY;
a hand-made ASCII PLY with CRLF line ends, a mid-header comment and an unused `alpha` property;
a hand-made ASCII PLY with mixed quad/triangle/pentagon faces under the alternative property name
`vertex_index`; a COFF file and a binary STL and an ASCII STL written from the same scan; three
SfS++ OBJs (two 17–31 MB with `f v/vt/vn`, one MeshLab file with per-vertex colours); two museum
GLBs read in full (all five were checked for the validation trap of §6); and two hand-made GLBs
carrying `COLOR_0` as normalized `u8` and as `f32`.

Reproduction: `/private/tmp/claude-501/…/scratchpad/rust/e2-io/` (`harness/` the Rust binary,
`py/run_all.py` the driver, `results.json` the full output). Nothing but this note is committed.

## 2. PLY — correctness

All four readers are **bit-identical to Open3D on every one of the 11 PLY files**, in file order,
including the colours, both raw and after cleaning. That covers ASCII and both binary byte orders,
`float` and `double` coordinates, extra properties that must be skipped (`nx ny nz`, `alpha`),
both list index types (`int` and `uint`), both property names (`vertex_indices`, `vertex_index`),
and polygon faces — Open3D triangulates an *n*-gon as a fan from its first vertex and so does every
reader's glue code here, giving the same 6 triangles for the quad/tri/pentagon file.

`mesh-loader` is not in that list because **it cannot read PLY**: 0.1.13 supports STL, COLLADA and
OBJ only, so D §3's "colour support in PLY unverified" is moot — there is nothing to verify.

## 3. PLY — speed and memory

Best read time in seconds; MB is the file size.

| file | MB | Open3D | own | `ply-rs-bw` | `serde-ply` | `ply-rs` |
|---|---|---|---|---|---|---|
| FY234007 (615 k v, 1.23 M f) | 25.2 | 0.084 | 0.024 | 0.057 | 0.063 | 0.691 |
| FY234021 | 21.6 | 0.071 | 0.020 | 0.047 | 0.058 | 0.596 |
| FY234094 (671 k v, 1.34 M f) | 27.5 | 0.091 | 0.026 | 0.062 | 0.071 | 0.765 |
| FY234104 | 14.5 | 0.049 | 0.014 | 0.031 | 0.036 | 0.388 |
| synthetic frag_000 (double + normals) | 24.2 | 0.057 | 0.014 | 0.033 | 0.035 | 0.492 |
| synthetic frag_003 | 27.6 | 0.064 | 0.015 | 0.037 | 0.042 | 0.560 |
| terracotta as ASCII | 29.0 | 0.178 | 0.082 | 0.216 | 0.198 | 0.765 |
| Open3D's own binary output | 18.8 | 0.050 | 0.013 | 0.033 | 0.041 | 0.381 |
| binary big-endian | 1.2 | n/a | 0.001 | 0.002 | 0.003 | 0.031 |

Peak RSS of the whole process on FY234094 (27.5 MB, 1.34 M faces), one read, no dump written:

| | own | `ply-rs-bw` | `serde-ply` | `ply-rs` |
|---|---|---|---|---|
| peak RSS | 61 MB | 105 MB | 104 MB | **1088 MB** |

The gate is "< 2 s per 25 MB PLY". `ply-rs-bw`, `serde-ply` and the own baseline clear it by
9–100×. `ply-rs` 0.1.3 clears it only on a quiet machine — under the load this experiment ran at
it took **2.02 s** on FY234094 once. It builds a `LinkedHashMap<String, Property>` per vertex and
per face, which is where both the 25–30× slowdown and the memory come from — 1.1 GB, ten times the
fork and forty times the file; on the 10 M-face scans D §1 budgets for, that shape would cost
several GB per fragment. `ply-rs` is rejected on
those two numbers alone, before its maintenance status (last release 2020-08-27, `peg` 0.6 from
2020) is considered.

`ply-rs-bw` is a maintained fork of it — same API family, `indexmap` instead of `linked-hash-map`,
`#![forbid(unsafe_code)]`, and CI that runs fuzzing, Miri and a check for breaking changes against
the published major. It reaches its speed through a typed `PropertyAccess` implementation (the
parser writes scalars straight into your struct); the `DefaultElement` map path is still there and
still slow, so the port must use the typed path. An attempt to save the per-face `Vec<u32>` by
parsing into a fixed `[u32; 4]` struct made it **slower** (0.118 s vs 0.096 s on FY234094) for
27 MB less peak RSS — the allocator handles the churn better than the copy does, so keep the
straightforward `Vec` form.

`serde-ply` matches `ply-rs-bw` on parity, speed and memory, and has the lighter dependency tree
(`serde`, `byteorder`, `thiserror` — no PEG parser generator). It loses on the writer (§4) and on
being pre-1.0 with an API that is a serde-derived struct per element, which means the reader has to
pick a struct from the header before deserializing (a mesh with and one without colours need two
types). It is the second choice, not the first.

## 4. PLY writing

`report.write_placed_meshes` calls `write_triangle_mesh(write_ascii=False, compressed=False,
write_vertex_normals=False)`. What Open3D actually emits for a coloured mesh is:

```
ply
format binary_little_endian 1.0
comment Created by Open3D
element vertex N
property double x
property double y
property double z
property uchar red
property uchar green
property uchar blue
element face M
property list uchar uint vertex_indices
end_header
```

— `double` coordinates, not `float`, and `uint` list values. A writer emitting `float` would be
half the size and *not* byte-compatible.

Writing the 354 k-vertex / 708 k-face terracotta mesh (18.77 MB output):

| writer | time | peak RSS | bytes identical to Open3D's file | Open3D re-reads it |
|---|---|---|---|---|
| own | 0.019 s | 36 MB | **yes** | identical arrays |
| `ply-rs-bw`, payload as slices | 0.029 s | 68 MB | **yes** | identical arrays |
| `ply-rs-bw`, element by element | 0.044 s | 42 MB | **yes** | identical arrays |
| `serde-ply` | 0.042 s | 67 MB | no — header says `uint8` / `uint32` | identical arrays |
| Open3D itself | 0.089 s | — | (reference) | — |

`ply-rs-bw` reproduces the reference file to the byte, and its `write_little_endian_element` lets
the merged assembly PLY of D §202 be streamed one member at a time without materialising a struct
per vertex. One footgun: `ElementDef::new` leaves `count` at 0 and `write_header` believes it, so a
file written without setting `ElementDef::count` gets a header claiming zero vertices while the
payload is complete — silently unreadable. Set it explicitly.

`serde-ply` writes the spec's alternative type spellings (`uint8`, `uint32` for `uchar`, `uint`)
with no option to choose the legacy names. Open3D reads the result back correctly, so it is a
valid PLY, but the file is not byte-comparable with the Python output and a diff-based regression
test on the outputs would fail.

## 5. OBJ, STL, OFF

| file | MB | Open3D | reader | time | raw vs Open3D | after cleaning |
|---|---|---|---|---|---|---|
| Pot_A_Piece_01 (200 k f) | 31.0 | 0.289 | `tobj` | 0.152 | 100 064 v vs 108 777 | counts exact, ≤ 1.8e-8 rel |
| | | | `mesh-loader` | 0.058 | 600 372 v | counts exact, ≤ 1.8e-8 rel |
| Pot_A_Piece_02 | 17.2 | 0.161 | `tobj` | 0.084 | 55 814 v vs 60 633 | counts exact, ≤ 1.9e-8 rel |
| Pot_C_Piece_01 (vertex colours) | 2.8 | 0.033 | `tobj` | 0.013 | 11 875 v vs 24 639, colours read | counts exact, colours exact |
| binary STL (60 k f) | 3.0 | 0.054 | `stl_io::read_stl` | 0.007 | 30 002 v vs 179 990 | **identical, same order** |
| | | | `stl_io` raw triangles | 0.001 | 180 000 v | identical, same order |
| | | | `mesh-loader` | 0.001 | 180 000 v | identical, same order |
| ASCII STL (5 k f) | 0.9 | — | `stl_io` | 0.006 | 2 818 v vs 14 998 | counts exact, ≤ 3.2e-8 rel |
| COFF (60 k f, colours) | 2.4 | 0.065 | own OFF reader | 0.009 | order preserved, colours exact | exact in f32 |

The raw column looks alarming and is not. **Open3D's vertex list for these formats is neither the
file's nor one vertex per face corner.** On an OBJ with 100 064 `v`, one `vn` per `v` and one `vt`
per face corner it returns 108 777 vertices in an order matching nothing in the file; on a binary
STL of 60 000 facets it returns 179 990 rather than 180 000, with no degenerate face and every
vertex referenced. The cause is almost certainly Assimp's vertex-joining pass: Open3D's binary
links `Assimp::JoinVerticesProcess` and carries `io/file_format/FileASSIMP.cpp`, and the counts do
not change with `enable_post_processing`. Nothing reproduces those numbers, and nothing has to —
`load_mesh` runs `remove_duplicated_vertices` immediately, and after that every reader agrees with
Open3D on the counts exactly and on the coordinates to within 2e-8 relative.

That residual is Open3D's, not the crates'. **Its ASCII-float parse is not correctly rounded** (the
Assimp readers use `fast_atof`): on Pot_A_Piece_01 the values it returns sit up to 1.5e-5 mm from
the correctly rounded `f64` of the same text *and* up to 7.6e-6 mm from the correctly rounded
`f32` — about a quarter of an `f32` ulp at those magnitudes, so they are not the rounding of either
type. **No reader can be bit-exact with Open3D on an ASCII input**, whatever precision it parses
at. In absolute terms the worst gap is 1.5e-5 mm, some 50× below D §10.2's tightest downstream
tolerance (1e-4·t, i.e. ~8e-4 mm at these wall thicknesses), and it disappears entirely once the
port stops comparing against Open3D and reads the files itself.

`tobj` is preferred over `mesh-loader` for OBJ despite being 2.5× slower: it returns the file's own
vertex list rather than one vertex per face corner, which is 6× less to allocate and 6× less for
the dedup pass to chew through. Two things the caller must get right — `load_obj` returns
`(models, Result<materials>)` and the material half must not be propagated (the SfS++ OBJs name a
`.mtl` that does not exist, and geometry loads fine without it); and it splits on `g`/`usemtl` into
models with per-model reindexed positions, so the models have to be concatenated with an index
offset.

For OFF there is no crate: `mesh-loader` does not support it, `tobj` does not, `meshx` 0.7 (the
only general mesh-exchange crate with real download numbers) covers `msh`/`obj`/`vtk` only, and a
keyword search of crates.io turns up nothing else. The own reader is 40 lines, handles `OFF`/`COFF`
with the 3- or 4-component colour rows Open3D writes, and matches the reference exactly at `f32`.

## 6. GLB

None of the five museum GLBs in `input/source_models/` actually carries `COLOR_0` — they are
textured (`POSITION`, `NORMAL`, `TEXCOORD_0`, 2–11 primitives, node transforms). The COLOR_0 path
was therefore tested against two hand-built GLBs, one with normalized `u8` and one with `f32`
colours; `gltf`'s `read_colors(0).into_rgba_u8()` reproduces Open3D's colours **exactly** for both.

Geometry: after cleaning, `gltf` matches Open3D exactly on `049_kelch` and to 8.8e-8 relative on
`025_zylinderhalsgefaess` (`f32` transform arithmetic). Reading 19.4 MB takes 0.013 s against
Open3D's 0.209 s.

Two traps, both mandatory to work around:

1. **Strict validation rejects a file for a reason that has nothing to do with geometry.**
   `Gltf::from_slice` refuses `025_zylinderhalsgefaess.glb` with `extensionsRequired[0] =
   "KHR_materials_pbrSpecularGlossiness": Unsupported extension` — a *material* extension, in a
   file whose positions and indices are perfectly ordinary. One museum file in five. Use
   `Gltf::from_slice_without_validation`, which reads all five.
2. **Node transforms must be applied.** Ignoring them and concatenating the primitives gives a
   mesh that does not match Open3D at all (`clean = MISMATCH` on `049_kelch`); walking the default
   scene and composing each node's matrix onto its children reproduces Open3D exactly.

Use `default-features = false, features = ["utils"]`: the default `import` feature pulls in
`image` 0.25 and `base64` to decode embedded textures the port never looks at, and dropping it
takes the transitive tree from 36 crates to 17. `Gltf::from_slice_without_validation` plus
`primitive.reader(|_| Some(blob))` on the GLB's own BIN chunk needs nothing more.

`gltf` 1.4.1 is the oldest release in the set (2024-05-10). It is also, by two orders of magnitude
of downloads, the standalone Rust glTF loader — the alternatives are engine-bound (`bevy_gltf`,
`three-d-asset`) — and GLB is the lightest-weight format here: read-only, used only for the
synthetic-fragment generator's source models, not in `MESH_EXT`. The risk is acceptable.

## 7. Why not the own PLY parser after all

D §3 chose an own PLY reader/writer, and on raw numbers it wins: 2.4× faster than `ply-rs-bw`
reading, 1.5× writing, 60 % of the peak RSS. The reason to drop it anyway:

- **The speed buys nothing.** Reading all four terracotta scans costs 0.20 s with `ply-rs-bw`
  against 0.08 s with the own reader, inside a preprocessing budget of ≤ 4 s *per fragment*
  (D §1) and a full run measured in hours. IO is not on any critical path in this pipeline.
- **The parity is identical.** Every criterion this experiment measures — counts, order, colours,
  byte-exact write — comes out the same for both.
- **The hardening is not free, and the crate has already paid for it.** The own baseline here
  panicked with `range end index 4 out of range` on a PLY truncated mid-payload, where `ply-rs`,
  `ply-rs-bw` and `serde-ply` all returned a clean error naming the position. That baseline was
  written for a speed measurement rather than for production, which is the point: bounds-checking
  every read of a header-declared count against the remaining buffer, and the property-type matrix
  behind it, is exactly the work `ply-rs-bw` fuzzes in CI. A museum collection will contain
  truncated and odd files.

If a profile ever shows PLY reading mattering — 170 fragments × 25 MB is about 9 s of `ply-rs-bw`
— the own reader can be brought back behind the same interface, with the crate as the fallback for
anything its fast path does not recognise.

## 8. Consequences for the design

1. **D §3 "mesh read" row:** replace "own PLY parser" with `ply-rs-bw` 4.0.1 (typed
   `PropertyAccess`, not `DefaultElement`); drop `mesh-loader` from consideration — it has no PLY
   support; keep `tobj` 4 and `stl_io` (pin 0.11.0); keep the own OFF reader; `gltf` 1.4.1 with
   `default-features = false, features = ["utils"]`.
2. **D §3 "mesh write" row:** `ply-rs-bw` writes Open3D's file byte for byte and streams element by
   element, so no own writer is needed. The layout to reproduce is `double` xyz + `uchar` rgb +
   `property list uchar uint vertex_indices`, **not** `float` xyz as the row says.
3. **D §10.2 load stage:** the "counts after cleaning — exact" gate is the right one and it passes
   for every recommended crate on every benchmark file. A raw-count comparison against Open3D would
   fail for OBJ, STL, OFF and GLB for reasons internal to Assimp; do not write that test.
4. **Coordinates from ASCII inputs (OBJ, OFF, ASCII STL) can differ from Open3D's by ~2e-8
   relative** and no implementation choice removes it, because Open3D's own parse is the inexact
   one. Parity fixtures for those formats need a tolerance, not an equality.
5. Pinned versions for S1's `Cargo.toml`: `ply-rs-bw = "4.0.1"`, `tobj = "4.0.5"`,
   `stl_io = "0.11.0"`, `gltf = { version = "1.4.1", default-features = false, features = ["utils"] }`.
