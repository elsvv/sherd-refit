# E7/E8 — wgpu feasibility on this Mac

**Date:** 2026-09-06. Branch `rust-core`. Plan row E7/E8 of
`docs/superpowers/plans/2026-09-06-rust-core-phase0-1a.md`; design references D §3 (E7, E8),
§6 (GPU plan), §6.8 (self-test), §7 (determinism).
Machine: Apple M2 Pro, 10 CPU cores, 16 GPU cores, 16 GB, macOS 15.6.1 (24G90), Metal 3.
Experiment code: `<scratchpad>/rust/E7/` (not committed; only this note is).

**Verdict: the E7 gate passes and the GPU path is worth building, with three corrections to the
design.**

1. **A fixed-order reduction of 1e7 f32 terms is bit-identical between Metal and the CPU, with
   stock wgpu, no flags** (§3). Both the strided-accumulate-then-tree schedule of D §6.4 and an
   explicitly ordered pairwise tree reproduce the CPU value bit for bit. Pure addition is not
   reassociated by anything in the naga → Metal path.

2. **But Metal compiles every shader with fast-math on, and wgpu does not turn it off** (§4).
   `a*b + c` is contracted into an FMA, division/sqrt/rsqrt are approximations good to 2 ULP, and
   denormals are flushed on both input and output. So D §6.7's "share the data layout and the
   traversal order and the two agree to a few ULPs" is only true for `+`/`-`; anything with a
   multiply-add diverges from a plain Rust mirror — on 27 % of isolated `a*b + c` evaluations,
   and on ~70 % of the accumulated quantities a real kernel produces. Two ways out are
   measured in §4.3: accept it (the deviation is 400× inside the §10.2 tolerances) or disable
   contraction with a ~15-line patch to `wgpu-hal`, which costs nothing measurable and makes the
   *whole* nearest-neighbour kernel bit-exact over 24.6 M queries.

3. **The GPU throughput assumption in D §6.6 is 5–10× optimistic** (§5). The design's own hash
   grid, at the design's own sizes, sustains **0.105 G bounded-NN queries/s**, not the 0.5–1 G/s
   the speedup table is built on. Against 4 CPU threads the GPU wins 8–11×; extrapolated to all
   10 cores that is roughly 4–5×. Still far above the 1.5× threshold `Backend::Auto` uses, but
   the "≈ 35 min of GPU time for the collection" line needs re-deriving after phase 2a.

E8 can only be half-answered here: this machine exposes exactly one adapter and no software
fallback of any kind (§6), so the vendor matrix has to wait for the CI runners.

## 2. Adapter and limits (D §6.8 self-test)

One adapter, Metal:

```
[0] backend=Metal name="Apple M2 Pro" device_type=IntegratedGpu vendor=0x0 device=0x0
    driver="" driver_info="" subgroup_min_size=4 subgroup_max_size=64
software (DeviceType::Cpu) adapter available: false
force_fallback_adapter: none ("metal had no fallback adapters")
```

`vendor`, `device`, `driver` and `driver_info` are all empty on Metal, so `--gpu-adapter NAME`
has only the adapter name to match on and the report cannot record a driver version.

| limit | this adapter | wgpu default |
|---|---|---|
| `max_compute_invocations_per_workgroup` | 1024 | **256** |
| `max_compute_workgroup_size` | 1024 × 1024 × 1024 | 256 |
| `max_compute_workgroups_per_dimension` | **65535** | 65535 |
| `max_compute_workgroup_storage_size` | 32768 B | **16384 B** |
| `max_buffer_size` | 4 GiB − 1 | 256 MiB |
| `max_storage_buffer_binding_size` | 4 GiB − 4 | 128 MiB |
| `max_uniform_buffer_binding_size` | 4 GiB − 1 | 64 KiB |
| `max_storage_buffers_per_shader_stage` | 29 | 8 |
| `max_bind_groups` | 8 | 4 |
| `min_storage_buffer_offset_alignment` | 32 | 256 |

Request `adapter.limits()` (it is accepted verbatim) but *write* the kernels to the wgpu
defaults, because that is what a portable build gets. Two consequences for D §6:

- D §6.8's worry is confirmed: 29 floats × 256 lanes = 29.7 KB of workgroup storage fits Metal's
  32 KB but **not** the 16 KB default. Design the ICP reduction for 16 KB (two passes of 128
  lanes) from the start, as the design already says.
- `max_compute_workgroups_per_dimension = 65535` is a hard wall, not a Metal quirk — it is also
  the wgpu default. The 4096-pose batch in §5 needs 96 000 workgroups and had to become a 2-D
  dispatch (`65535 × 2`) with the linear index recomputed as `gid.x + gid.y * wg_x * 256`. Any
  batch kernel in `sherd-gpu` needs that fallback (or per-chunk offsets) from day one.

Features: `TIMESTAMP_QUERY` yes (but see §7), `SHADER_F16` yes, `SHADER_INT64` yes, `SUBGROUP`
yes, `MAPPABLE_PRIMARY_BUFFERS` yes; `TIMESTAMP_QUERY_INSIDE_ENCODERS`,
`TIMESTAMP_QUERY_INSIDE_PASSES`, `PIPELINE_STATISTICS_QUERY` and **`SHADER_F64`** no. f64 on the
GPU is off the table, as D §6.8 already assumes.

Host↔device transfer of a 64 MiB buffer on this unified-memory part: **4.9 GB/s** up
(`create_buffer_init`, mapped at creation) and **2.9 GB/s** back
(`copy_buffer_to_buffer` + `map_async`). Both are driver-overhead-bound rather than
bandwidth-bound, and both are far more than D §6.3 needs (fragment slots are uploaded once per
epoch and readback is a few hundred KB per batch).

## 3. E7: fixed-order reduction, bit-for-bit

10 000 000 f32 terms, values uniform in [−1, 1) with every 997th scaled by 1e5 so that summation
order genuinely matters (the two schedules below differ from each other by 2 ULP, and both differ
from the f64 reference −8468089.55 in the third significant digit).

Two schedules, each with an exactly mirrored single-threaded Rust implementation:

- **naive**: 256 workgroups × 256 lanes; lane `l` of workgroup `w` accumulates
  `a[w·block + l], a[w·block + l + 256], …` sequentially, then a shared-memory tree
  256 → 128 → … → 1, then a second dispatch reduces the 256 partials with the same tree.
  This is exactly the striding and reduction tree D §6.4/§6.7 specify.
- **ordered tree**: one workgroup folds 512 contiguous elements as a balanced binary tree
  (`sh[lane] = in[base+2l] + in[base+2l+1]`, then the same 256 → 1 tree); the host repeats the
  pass, 10 000 000 → 19 532 → 39 → 1.

| schedule | per-workgroup partials | final value |
|---|---|---|
| naive strided | **bit-identical**, 256/256 | **bit-identical**, −8468091.0 (`0xcb01367b`) |
| ordered tree | **bit-identical**, 19 532/19 532 | **bit-identical**, −8468089.0 (`0xcb013679`) |

This holds in stock configuration and in all four compiler configurations of §4.3. **The E7 pass
criterion is met.** Neither the Metal compiler nor naga reassociates or vectorises a scalar f32
accumulation loop, and workgroup-memory tree reductions are exact.

Forcing strict ordering, in practice: nothing special is needed for addition. What you must not
do is let the *shape* drift — the kernel and its CPU mirror have to agree on the workgroup count,
the lane stride, the loop bound, and the tree. All four are data in the batch descriptor, so make
them explicit fields rather than derived constants, and never use subgroup reduction intrinsics
(`subgroupAdd` and friends have no defined order) or floating-point atomics. D §7 already says
this; E7 confirms it is sufficient.

## 4. What the Metal compiler actually does to the arithmetic

### 4.1 The compile path

`wgpu-hal-30.0.1/src/metal/device.rs:272` builds `MTLCompileOptions`, sets only
`languageVersion` and (on macOS ≥ 11) `preserveInvariance`, and compiles. It never touches
`fastMathEnabled` or `mathMode`, so **Metal's default applies, and Metal's default is fast**.
On the naga side there is no counterweight either: the MSL writer emits no `precise` qualifier
and the SPIR-V writer emits no `NoContraction` decoration (grepped in naga 30.0.0). naga's MSL
for `x * y + z` is literally `(x * y) + z`; everything after that is clang's choice.

### 4.2 Measured behaviour (61 440 random values, stock configuration)

| probe | result |
|---|---|
| `x*y + z` vs CPU `x*y + z` | 16 685 mismatches |
| `x*y + z` vs CPU `x.mul_add(y, z)` | **0 mismatches** → the compiler contracts to FMA |
| explicit WGSL `fma(x,y,z)` vs CPU `mul_add` | 0 mismatches |
| `x / y` vs IEEE division | 18 252 mismatches, max **2 ULP** |
| `sqrt(x)` vs IEEE sqrt | 19 415 mismatches, max **2 ULP** |
| `1/sqrt(x)` vs IEEE | 18 599 mismatches, max **2 ULP** |
| `dot(v,v)` vs CPU `x*x+y*y+z*z` | 13 672 mismatches |
| `dot(v,v)` vs `fma(z,z, fma(y,y, x*x))` | **0 mismatches** → left-to-right fused chain |
| subnormal × 2.0 | **4096/4096 flushed to zero** (FTZ on the result) |
| subnormal × 1e30 | **4096/4096 flushed to zero** (DAZ on the input) |

At scale the same thing: the strided weighted sum `acc = acc + a[i]*b[i]` over 1e7 terms differs
from a plain Rust mirror in 152 of 256 workgroup partials (max |Δ| 6.25e-2 on partials of order
2e5) and is **bit-identical** to a Rust mirror written with `mul_add`.

Two practical rules follow regardless of which option §4.3 picks:

- **Do not use `dot`, `length`, `distance`, `normalize` in WGSL where parity matters.**
  `metal::dot` is a library function; it stays fused even when contraction is disabled in the
  calling translation unit. Write the sum out explicitly, or mirror the exact fused chain
  (`fma(z,z, fma(y,y, x*x))`) on the CPU. The kernel in §5 writes it out.
- **Do not rely on denormals.** Apple GPUs flush them in hardware; no compiler option changes
  that. Nothing in R produces f32 denormals at these scales (coordinates are 1e-3…1e2), but a
  `normalize` of a near-zero vector or a `1/x` guard would.

### 4.3 How to force strict ordering, if it is wanted

Three knobs exist. All were tested by patching a vendored `wgpu-hal` (about 15 lines in
`create_shader_module`) and switching them with environment variables:

- `MTLCompileOptions::setMathMode(MTLMathMode::Safe)` (macOS ≥ 15; `setFastMathEnabled(false)`
  on older systems)
- `MTLCompileOptions::setMathFloatingPointFunctions(Precise)` (macOS ≥ 15)
- prepending `#pragma clang fp contract(off)` to the generated MSL, either at file scope or
  inside every kernel body

| configuration | `x*y+z` | `/` | `sqrt` | `1/sqrt` | denormals |
|---|---|---|---|---|---|
| stock wgpu 30.0.1 | fused | 2 ULP | 2 ULP | 2 ULP | flushed |
| `MathMode::Safe` + `Precise` | fused | exact | exact | exact | flushed |
| file-scope `contract(off)` | **not fused** | 2 ULP | 2 ULP | 2 ULP | flushed |
| `MathMode::Safe` + file-scope pragma | fused (**pragma lost**) | exact | exact | exact | flushed |
| `Precise` + file-scope pragma | **not fused** | 2 ULP | exact | 2 ULP | flushed |
| **`MathMode::Safe` + `Precise` + per-function pragma** | **not fused** | **exact** | **exact** | **exact** | flushed |

The quirk in row 4 is worth remembering: setting `mathMode` makes the driver pass an explicit
`-ffp-contract` on the command line, which beats a *file-scope* pragma. Moving the pragma to the
top of each kernel body (a statement-level `#pragma clang fp`) wins again, and the last row is
the configuration that gives IEEE semantics for everything except denormals.

Cost of the last row, measured on the §5 kernel over 24.6 M queries: **9.13 ns/query strict vs
9.42 ns/query stock** — i.e. none, within run-to-run noise on a machine shared with other jobs.

**Recommendation.** Keep the team's tolerance-based parity (D §10.2) as the production contract:
§5 shows the stock-fast-math deviation is 400× inside the tightest distance tolerance. But treat
the strict configuration as a *debugging* backend worth having, because it turns "the GPU and CPU
should agree to a few ULPs" into "the GPU and CPU agree bit for bit", which makes a kernel
mismatch in CI a real signal instead of a tolerance argument. It needs a `wgpu-hal` fork, so the
honest options are (a) carry a small patch behind a cargo feature, (b) upstream an
`InstanceFlags::STRICT_FLOAT_MATH` to wgpu, or (c) skip it. Note also that the patch only fixes
Metal; the equivalent knobs for Vulkan (SPIR-V `NoContraction` / `SignedZeroInfNanPreserve`) and
DX12 (DXC `-ffp-contract`) are not emitted by naga either, so option (b) is the only one that
scales to the whole matrix.

## 5. Batched radius-bounded nearest-neighbour micro-kernel

The kernel is D §6.2's hash grid verbatim: cell size = radius, key
`(ix·73856093) ^ (iy·19349663) ^ (iz·83492791)`, open addressing into `cap = next_pow2(2n)`
slots, `(ix, iy, iz, start)` + `counts` + `sorted_idx` with points ascending by original index
inside a cell, 27 neighbour cells in fixed `(dx, dy, dz)` order, ties broken by lowest index.
One GPU invocation per (pose, source point), workgroup 256. The CPU comparison is the same
algorithm in Rust under rayon.

Data: 6000 target and 6000 source points on a warped unit sheet (a stand-in for a fracture
surface), radius 0.03, grid capacity 16 384 with **1305 occupied cells, at most 14 points per
cell, 46.1 candidate points examined per query**, hit rate 97.6–100 %. Poses are small random
rigid perturbations.

| poses | queries | GPU wall (mean) | ns/query | GPU per pose | CPU 1 thr | CPU 4 thr | GPU vs 4 thr |
|---|---|---|---|---|---|---|---|
| 1 | 6 000 | 0.65 ms | 108.6 | 652 µs | 415 ns/q | 362 ns/q | 3.3× |
| 8 | 48 000 | 0.72 ms | 14.9 | 89 µs | 399 ns/q | 137 ns/q | 9.2× |
| **64** | **384 000** | **4.70 ms** | **12.2** | **73 µs** | 326 ns/q | 100 ns/q | **8.1×** |
| 256 | 1 536 000 | 14.61 ms | 9.5 | 57 µs | 327 ns/q | 106 ns/q | 11.2× |
| 1024 | 6 144 000 | 58.26 ms | 9.5 | 57 µs | — | 79 ns/q | 8.3× |
| 4096 | 24 576 000 | 231.5 ms | 9.4 | 57 µs | — | 98 ns/q | 10.4× |

The CPU columns are noisy (the machine was shared with other agents; single-thread cost ranged
255–415 ns/query across repeats). Take the GPU numbers as solid and the CPU ones as ±40 %.

Reading the table:

- **Saturated GPU throughput is 105–110 M queries/s (9.4 ns/query)**, reached from ~256 poses up.
  At 46.1 candidates per query that is 4.9 G candidate distance tests/s and 2.9 G cell probes/s.
  D §6.6 assumes "0.5–1 G bounded NN queries/s on the hash grid"; the measured figure is 5–10×
  lower. The kernel is latency-bound on the gathers, not ALU-bound.
- **The 27 cell lookups alone cost 2.8–3.2 ns/query, 26–34 % of the kernel** (measured with a
  variant that does the lookups and sums the counts but no distance arithmetic). So a third of
  the time goes to finding cells, before a single distance is computed. If the GPU path ever
  needs to be faster, that is where to look — a dense cell index for small clouds, or folding the
  27 probes into fewer by storing 2×2×2 blocks.
- **Submit + `poll(Wait)` costs ≈ 0.5 ms**, which dominates any dispatch below ~50 k queries
  (the 1-pose row is 108 ns/query, 11× the saturated rate). Batching 16 dispatches into one
  command buffer brings the 1-pose case to 0.143 ms/dispatch. D §6.4's plan of one dispatch per
  rung for a whole block of pairs is the right shape; per-pair dispatches would not be.
- **Dispatch sizing for the 100 ms budget** (D §6.4, Windows TDR): 100 ms / 9.4 ns ≈ **10.6 M
  queries per dispatch**, i.e. ≈ 1700 poses × 6000 points. The design's chunk of ≤ 512 ICP
  candidates is comfortably inside that for the correspondence search; the ICP rung kernel also
  carries the solve, so it needs its own measurement in phase 2a.
- **Per pose, 6000 points against 6000: 57 µs on the GPU vs ~480–640 µs on 4 CPU threads.**
  Scaling the CPU to 10 cores (≈ 2× at best over 4 threads on this memory-bound loop) leaves the
  GPU 4–5× ahead. That clears D §6.8's 1.5× `Backend::Auto` bar with room, but it is not the
  15–50× the D §6.6 table implies.

### 5.1 Parity of this kernel, CPU vs GPU

Stock configuration, against a plain-Rust mirror (`d2 = dx*dx + dy*dy + dz*dz`):

| poses | index mismatches | `d2` bit mismatches | max abs Δd2 | max abs Δd |
|---|---|---|---|---|
| 64 | 0 / 384 000 | 275 741 | 6.8e-9 | 1.6e-7 |
| 1024 | 15 / 6 144 000 | 4 344 148 | 1.14e-8 | 2.3e-7 |
| 4096 | 56 / 24 576 000 | 1.74e7 | 1.14e-8 | **2.4e-7** |

The cloud spans 1 unit, so `max |Δd| = 2.4e-7 t` — over 400× inside the tightest
distance tolerance in D §10.2 (1e-4 t for the breakline Hausdorff, 0.002 t for `gap`). The
disagreement that matters is not the distance but the **choice of neighbour**: 2.3e-6 of queries
pick a different point when two candidates are within a ULP of each other. That is inherent to
tolerance-based parity and is exactly what D §7's "NN ties → lowest index" rule cannot fix, since
the tie is not exact on one of the two sides.

Mirroring the fused chain on the CPU (`fma(dz,dz, fma(dy,dy, dx*dx))`) does *not* fix it either —
still ~70 % bit mismatches — because the pose transform `R·p + t` is contracted too, so the
transformed point already differs. Reproducing Metal's contraction expression by expression is
possible but brittle.

With the strict configuration of §4.3, over the whole sweep: **0 index mismatches, 0 `d2` bit
mismatches, 0 `sqrt(d2)` bit mismatches out of 24 576 000 queries**, at no time cost. That is the
concrete evidence behind the recommendation in §4.3.

## 7. Driver and toolchain quirks worth writing down

1. **Timestamp queries return nonsense.** `TIMESTAMP_QUERY` is advertised, the pass-boundary
   writes resolve without error, and the values are wrong: 0.000 ms for kernels whose wall time
   is 0.65–4.7 ms, then 3.997 / 1.006 / 191.586 ms for kernels whose wall time is 14.6 / 58.3 /
   231 ms. Do not build `Backend::Auto`'s throughput measurement (D §6.8) on them; time
   `submit` + `poll(Wait)` on the host instead, with a dispatch large enough (≥ 50 k queries) to
   swamp the 0.5 ms submit cost.
2. **`TIMESTAMP_QUERY_INSIDE_ENCODERS` and `_INSIDE_PASSES` are unavailable on Metal**, so
   per-stage timing inside one command buffer is not an option there.
3. **Auto pipeline layouts are exclusive.** A bind group built from
   `pipeline_a.get_bind_group_layout(0)` is rejected for `pipeline_b` even when the bindings are
   identical ("Exclusive pipelines don't match"). Any module with several entry points sharing
   buffers — which is every kernel file in D §6.5 — needs an explicit `BindGroupLayout` +
   `PipelineLayout`. Also: a derived layout only contains the bindings that entry point actually
   *uses*, so the bind group must be built to match, which is a second reason to go explicit.
4. **naga rejects a function whose `loop` never falls through** without a trailing `return`
   (`InvalidReturnType`). The hash-probe loop needed a dead `return -1;` after it.
5. **naga injects a loop-bound counter into every `loop`** (`Options::force_loop_bounding`,
   default true): two extra instructions and a `uint2` per loop, visible in the generated MSL as
   `loop_bound`. It can be disabled in `naga::back::msl::Options` but wgpu does not expose that,
   so the hot 27-cell loop carries it. Worth remembering when §5's numbers are compared against a
   hand-written Metal kernel.
6. **Metal reports no vendor, device id, driver or driver_info**, so a run report cannot record
   a driver version on macOS and `--gpu-adapter` can only match on the name.

## 8. What to change in the design

- D §3, GPU row: `wgpu` **30.0.1** (pinned exactly), `bytemuck` 1, `pollster` 0.4; Rust ≥ 1.87;
  do not pin wgpu 28.0.0 (MSRV 1.92).
- D §6.6: replace the "0.5–1 G bounded NN queries/s" basis with the measured
  **0.105 G queries/s at 46 candidates per query** (equivalently 4.9 G candidate tests/s), and
  re-derive the GPU column. The GPU still wins, by roughly 4–5× over the whole 10-core CPU on
  this kernel rather than the order of magnitude the table implies.
- D §6.4: add the `max_compute_workgroups_per_dimension = 65535` fallback (2-D dispatch or
  per-chunk offsets) to the batch-formation rules; it is hit at 96 000 workgroups, which a
  4096-candidate batch reaches.
- D §6.7: soften "expected to agree to a few ULPs" to what E7 actually shows — bit-identical for
  addition-only reductions, and `2.4e-7 t` distance-level agreement with ~2e-6 of nearest-
  neighbour choices differing, unless the strict-math patch of §4.3 is carried. Add the "no
  `dot`/`length`/`normalize` in parity-critical WGSL" rule.
- D §6.8: the self-test should use host wall time, not timestamp queries; and it should record
  that no software adapter exists on macOS, so a Metal self-test failure means CPU fallback with
  no second opinion available.

## 9. Independent re-run (same day, same binary, lighter machine load)

The whole experiment was re-executed end to end after the sections above were written, to
separate the findings from run-to-run noise on a machine shared with other agents. Every
qualitative claim reproduced; the quantitative spread is recorded here so phase 2a knows which
digits to trust.

| quantity | first run (§2–§5) | re-run | verdict |
|---|---|---|---|
| naive strided reduction, 1e7 terms | bit-identical, `0xcb01367b` | bit-identical, `0xcb01367b` | **stable** |
| ordered tree reduction | bit-identical, `0xcb013679` | bit-identical, `0xcb013679` | **stable** |
| all ten FP probes of §4.2 | as tabulated | identical counts, to the value | **stable** |
| strict config (§4.3 last row) | `x*y+z` unfused, div/sqrt/rsqrt exact, denormals flushed | identical | **stable** |
| strict NN parity, 24.6 M queries | 0 index, 0 `d2` bit, 0 `sqrt` bit | **0 / 0 / 0** | **stable** |
| stock NN parity, 24.6 M queries | 56 index mismatches, max abs Δd 2.4e-7 | 56 index, 2.372e-7 | **stable** |
| saturated GPU throughput | 9.4–9.5 ns/query (105–110 M/s) | 8.95–8.99 ns/query (111 M/s) | ±5 %, load-dependent |
| GPU per pose at 4096 poses | 57 µs | 53.7 µs | ±6 % |
| strict vs stock kernel cost | 9.13 vs 9.42 ns/query | 8.97 vs 8.95 ns/query | **no cost, confirmed** |
| host→device / device→host | 4.9 / 2.9 GB/s | 4.6 / 2.5 GB/s | ±15 %, driver-overhead-bound |
| CPU 4-thread, 4096 poses | 98 ns/query | 116.8 ns/query | ±20 %, as warned |

So: **every bit-parity result is exactly reproducible, and only the timings move.** Quote the GPU
throughput as **9.0–9.5 ns/query (105–111 M bounded-NN queries/s)** rather than a single figure,
and keep the §5 conclusion that D §6.6 is 5–10× optimistic — the re-run moves the number by 5 %,
not by the factor that would rescue the design's estimate. The CPU columns remain the least
trustworthy part of the table; the 4-core figure should be re-measured on a quiet machine before
the `Backend::Auto` threshold is tuned.

Reproduce with (`<scratchpad>/rust/E7`, `cargo build --release`):

```
./target/release/e7_wgpu selftest   # §2  adapter, limits, features, transfer
./target/release/e7_wgpu e7         # §3  reduction parity + §4.2 FP probes
```
